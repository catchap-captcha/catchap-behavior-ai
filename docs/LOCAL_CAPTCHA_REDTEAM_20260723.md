# 로컬 CAPTCHA 행동 AI 레드팀 실험 기록

## 1. 문서 목적

메인 이미지 드래그 CAPTCHA와 행동 AI를 로컬에서 연결한 뒤, 자동 브라우저
조작을 사람 행동으로 오인하는지 확인한 실험을 기록한다.

- 실험 일시: 2026-07-23 KST
- 실험 범위: 로컬 테스트 환경만 사용
- 목표: 정답을 맞힌 자동화 궤적이 행동 AI의 `allow` 판정을 받을 수 있는지 확인
- 성공 조건: 정답 검증 성공과 행동 AI `recommended_action=allow` 동시 만족
- 실패 조건: `step_up` 또는 `step_up_and_rate_limit` 판정으로 로컬 차단

이 문서의 결과는 운영 배포 성능을 의미하지 않는다. 현재 로컬 프록시는
레드팀 실험을 위해 `step_up`도 차단하도록 설정되어 있다.

## 2. 테스트 구성

```text
Chrome 자동 조작
  -> 로컬 CAPTCHA 프록시 :18001
  -> 메인 CAPTCHA API 터널 :18000
  -> GPU 서버 메인 CAPTCHA :8000

로컬 CAPTCHA 프록시 :18001
  -> 로컬 행동 AI :8010
  -> 모델 점수와 위험 판정 수신
  -> 테스트 모드에서 step_up 이상이면 CAPTCHA 검증 전에 차단
```

관련 파일:

- `scripts/local_captcha_shadow_proxy.py`
- `scripts/run_local_shadow_test.command`
- `scripts/run_local_block_test.command`
- `app/api/predict.py`
- `app/services/quality_validator.py`
- `app/services/risk_fusion.py`
- `../ai-service-ms-behavior/app/behavior_client.py`
- `../ai-service-ms-behavior/app/main.py`

자동 원시 기록:

```text
output/redteam/local_captcha_redteam_20260723.jsonl
```

프록시를 다시 시작한 뒤부터 각 검증 시도는 위 JSONL에 자동 누적된다.
기록에는 모델 입력용 포인터 이벤트, 문제 크기, 이벤트 종류별 개수, 원본
점수와 프록시 결과가 포함된다. 백엔드 인증 키와 정답 역할은 저장하지 않고,
세션 ID는 SHA-256 해시로만 저장한다. 경로는 `REDTEAM_LOG_PATH` 환경변수로
변경할 수 있다.

로컬 실행 모드:

```text
LOCAL_ENFORCEMENT_MODE=block_step_up_for_test
```

이 모드는 운영 정책이 아니라 레드팀 확인용이다. `recommended_action`이
`step_up` 또는 `step_up_and_rate_limit`이면 프록시가 메인 CAPTCHA 검증
요청을 전달하지 않고 로컬 차단 응답을 반환한다.

## 3. 현재 모델과 판정 기준

| 항목 | 값 |
|---|---|
| 모델 | `lightgbm_general_dynamics_min_fusion` |
| 모델 버전 | `revalidation_two_view_participant_safe_20260722` |
| Feature schema | `2.3` |
| 기본 Human 임계값 | `0.9999500521595306` |
| Step-up 해제 임계값 | `0.9999955746270602` |
| Medium risk 시작점 | `40` |
| High risk 시작점 | `70` |

주요 판정:

- Human score가 기본 임계값 미만이면 `ml_bot_score`
- 기본 임계값 이상이지만 step-up 해제 임계값 미만이면 `ml_step_up_band`
- 서버가 기록한 문제 발급·제출 시각 밖의 이벤트면
  `invalid_event_telemetry`로 최소 `step_up`
- 현재 로컬 테스트에서는 두 경우 모두 최종 통과하지 못함
- 화면의 Human 값은 소수점 셋째 자리까지만 표시되므로 `1.000`이어도 실제
  값이 step-up 해제 임계값보다 낮을 수 있음

## 5. 현재까지 확인한 핵심

1. 단순 직선과 단순 곡선 자동화는 현재 모델이 강하게 탐지한다.
2. 약 20점의 부드러운 곡선과 끝점 보정을 사용한 시도 C는 모델 점수를
   사실상 사람 수준까지 올렸다.
3. 시도 C가 최종 통과하지 못한 이유는 다른 고급 신호가 아니라
   `ml_step_up_band` 하나였다.
4. 화면 반올림 값만 보면 Human `1.000`으로 보이지만 실제 값은
   `0.999955`이므로 반드시 원본 점수를 함께 기록해야 한다.
5. 30점 S자형처럼 복잡성을 무작정 높이는 전략은 성능을 악화시켰다.
6. 현재 모델의 약점 후보는 "적당한 수의 점으로 만든 부드러운 곡선과
   작은 끝점 보정"이다.
7. 20점 곡선의 높은 사람 점수는 다른 문제에서 동일하게 재현되지 않았으며,
   문제의 이동 방향과 거리에 대한 민감도가 존재한다.
8. 프론트는 `pointer_move`를 약 40ms 간격으로 제한하므로 입력 경로의 점을
   늘려도 실제 모델 표본 수가 같은 비율로 증가하지 않는다.
9. 드래그가 이미지 영역을 벗어나 오른쪽 정답존으로 이동하면 정규화 `x`가
   `1.0`으로 고정된다. 시도 F에서는 마지막 네 이동점의 `x=1.0`이어서
   정답존 접근 구간의 수평 형태 정보가 손실됐다.
10. 고정 레드팀 후보를 브라우저 이벤트 대신 제출하면 정답과 행동 AI
    `allow`가 동시에 성립하므로 실제 우회 취약점이 존재했다.
11. 해당 우회의 직접 원인은 클라이언트가 보낸 행동 이벤트의 출처와 시각을
    서버가 검증하지 않았다는 점이다.
12. 서버 시간 바인딩 후 같은 상대시각 후보는 모델 점수와 관계없이
    `invalid_event_telemetry`로 `step_up` 처리된다.

## 6. 적용한 보완

### 6.1 CAPTCHA 서버의 신뢰 시각 전달

`ai-service-ms-behavior` 연동 계층에서 다음 시각을 행동 API에 전달한다.

- `presented_at`: DB에 저장된 challenge `created_at`
- `submitted_at`: verify 요청을 서버가 실제로 받은 시각

브라우저가 이 두 값을 정하지 않으며, 기존 세션 ID·challenge ID와 함께
행동 요청에 묶인다.

### 6.2 행동 API의 이벤트 시간창 검증

온라인 예측 API는 첫 이벤트와 마지막 이벤트가 서버가 기록한 문제 수명
안에 있는지 확인한다. 허용 오차는 현재 `5,000ms`다.

- 이벤트가 문제 발급 전이거나 제출 후이면 거부
- 이벤트 자체 지속 시간이 서버 관측 시간보다 길면 거부
- 서버 발급·제출 시각이 누락된 온라인 예측 요청도 거부
- 학습 수집 API는 기존 상대시각 데이터를 보존하기 위해 이 강제 검사를
  적용하지 않음

### 6.3 품질 거부와 위험 점수 결합

이전에는 품질 검사에서 `rejected`여도 모델 점수가 높으면 `allow`가 가능했다.
이제 온라인 예측에서 품질 거부가 발생하면:

- 이유에 `invalid_event_telemetry` 추가
- 위험 점수를 최소 `medium`으로 보정
- 권고 동작을 최소 `step_up`으로 제한

### 6.4 단순 프레임 규칙을 채택하지 않은 이유

최고 후보는 시간 간격 중복 비율이 높지만, 이 값만으로 차단하면 정상
사용자 오탐이 너무 커졌다.

| 규칙 | 정상 사용자 FRR | 레드팀 후보 탐지율 |
|---|---:|---:|
| 이벤트 40개 이상 + 중복 간격 0.90 이상 | `29.88%` | `79.78%` |
| 이벤트 40개 이상 + 중복 간격 0.95 이상 | `4.05%` | `43.82%` |

정상 사용자 FRR 목표 `3% 이하`를 만족하지 못하므로 이 규칙을 운영 차단에
사용하지 않았다.

### 6.5 자동 테스트 결과

- 행동 AI 전체 테스트: `183 passed`
- CAPTCHA 행동 연동 테스트: `6 passed`
- 추가 확인:
  - 서버 시간창 안의 절대시각 이벤트는 `valid`
  - 상대시각 또는 오래된 이벤트는 `rejected`
  - 서버 시각이 누락된 온라인 검증도 `rejected`
  - 품질이 거부된 고득점 모델 결과도 `allow`가 아닌 `step_up`

## 7. CAPTCHA UI에서 발견한 별도 결함

다음 문제는 행동 AI 점수와 별개로 메인 CAPTCHA 사용성과 데이터 품질에
영향을 준다.

### 레터박스 이미지와 드래그 영역 불일치

- 세로 사진이 가로 stage 안에 표시될 때 실제 이미지 양쪽에 빈 영역이 생김
- 객체 hit region은 stage 전체 비율로 배치되어 화면의 객체와 어긋남
- 화면에서 자전거를 탄 사람을 잡았지만 선택되지 않거나 다른 사람이 선택됨
- 빨간 반바지 사람을 잡았지만 검은 반바지 사람이 선택됨
- 두 시도는 정답이 보장되지 않아 행동 AI 검증에는 제출하지 않음

영향:

- 정상 사용자가 오답 객체를 선택하게 되어 CAPTCHA 정답률이 낮아짐
- 잘못된 객체를 다시 잡는 행동이 봇 feature로 오인될 수 있음
- 행동 데이터 라벨 품질이 나빠져 모델 검증을 오염시킴

보완 방향:

- 이미지가 실제로 그려진 content box 기준으로 hit region을 변환
- `object-fit: contain`의 좌우 또는 상하 여백을 좌표 계산에 반영
- 다양한 종횡비에서 bbox 시각 회귀 테스트 추가

## 8. 보안 관점의 판단

시도 H에서 실제 정답 검증과 행동 AI `allow`를 동시에 통과했다. 따라서
보완 전 상태는 배포 가능한 방어 완료 상태가 아니었다.

이번 서버 시간 바인딩은 확인된 고정 후보를 실제 종단간 테스트에서도
`step_up`으로 바꿨지만 완전한 행동 출처 증명은 아니다. 공격자가 이벤트
시각을 현재 challenge 시간창에
맞춰 다시 작성하면 클라이언트 제출형 API만으로는 진위를 확정할 수 없다.
브라우저 안에 넣은 서명 키도 공격자에게 노출되므로 해결책이 되지 않는다.

또한 현재 로컬 차단은 `step_up`을 강제로 실패 처리한 결과다. 운영 환경에서
`step_up`이 추가 CAPTCHA만 요청하도록 구성되면 자동화가 다음 문제를 계속
풀 수 있으므로, 반복 시도 제한과 세션 단위 위험 누적이 함께 필요하다.

최종적으로는 서버가 이벤트를 제출 시점에 한꺼번에 받는 방식이 아니라,
수집 중에 순서와 도착 시각을 직접 기록해야 한다. 모델 점수는 이 신뢰 가능한
프로토콜 신호와 결합할 때만 운영 차단 근거로 사용할 수 있다.

상세 구현 계약은 `docs/BEHAVIOR_EVENT_TRUST_PROTOCOL.md`에 기록했다.

## 9. 다음 실험 계획

1. 상대시각 후보뿐 아니라 현재 시간창으로 이동한 후보를 별도 외부
   holdout으로 만들어 이번 보완의 한계를 검증한다.
2. 이벤트를 소량 배치 또는 WebSocket으로 수신하면서 서버 도착 시각과
   증가하는 sequence를 기록하는 수집 API를 설계한다.
3. 일회성 challenge nonce, 세션 바인딩, 성공·실패와 무관한 challenge 소비,
   요청 빈도 제한을 메인 CAPTCHA 서버에서 함께 검증한다.
4. 기존 최고 후보는 학습·임계값 튜닝에 사용하지 않고 고정 회귀 holdout으로
   계속 보존한다.
5. 보완 후 Human FRR `3% 이하`, 알려진 Bot ASR `5% 이하`, 미지 family 최악
   ASR `10% 이하`를 같은 고정 기준으로 다시 계산한다.

## 10. 실험 기록 원칙

앞으로 각 시도에 다음 항목을 반드시 추가한다.

- 시도 번호와 시각
- 문제 문구와 정답 객체 수
- 궤적 유형과 점 개수
- 드래그 전 이동과 끝점 보정 여부
- Human score와 Bot risk score 원본 값
- Risk score, risk level, recommended action
- `reasons`
- 정답 성공 여부와 행동 AI 최종 통과 여부
- 이전 시도 대비 변화와 해석
