# 로컬 CAPTCHA 행동 AI 레드팀 실험 기록

## 1. 문서 목적

메인 이미지 드래그 CAPTCHA와 행동 AI를 로컬에서 연결한 뒤, 자동 브라우저
조작을 사람 행동으로 오인하는지 확인한 실험을 기록한다.

- 실험 일시: 2026-07-23 KST
- 실험 범위: 로컬 테스트 환경만 사용
- 목표: 정답을 맞힌 자동화 궤적이 행동 AI의 `allow` 판정을 받을 수 있는지 확인
- 성공 조건: 정답 검증 성공과 행동 AI `recommended_action=allow` 동시 만족
- 실패 조건: `step_up` 또는 `step_up_and_rate_limit` 판정으로 로컬 차단

이 문서의 결과는 운영 배포 성능을 의미하지 않는다. 현재 로컬 프록시는
레드팀 실험을 위해 `step_up`도 차단하도록 설정되어 있다.

## 2. 테스트 구성

```text
Chrome 자동 조작
  -> 로컬 CAPTCHA 프록시 :18001
  -> 메인 CAPTCHA API 터널 :18000
  -> GPU 서버 메인 CAPTCHA :8000

로컬 CAPTCHA 프록시 :18001
  -> 로컬 행동 AI :8010
  -> 모델 점수와 위험 판정 수신
  -> 테스트 모드에서 step_up 이상이면 CAPTCHA 검증 전에 차단
```

관련 파일:

- `scripts/local_captcha_shadow_proxy.py`
- `scripts/run_local_shadow_test.command`
- `scripts/run_local_block_test.command`
- `app/api/predict.py`
- `app/services/quality_validator.py`
- `app/services/risk_fusion.py`
- `../ai-service-ms-behavior/app/behavior_client.py`
- `../ai-service-ms-behavior/app/main.py`

자동 원시 기록:

```text
output/redteam/local_captcha_redteam_20260723.jsonl
```

프록시를 다시 시작한 뒤부터 각 검증 시도는 위 JSONL에 자동 누적된다.
기록에는 모델 입력용 포인터 이벤트, 문제 크기, 이벤트 종류별 개수, 원본
점수와 프록시 결과가 포함된다. 백엔드 인증 키와 정답 역할은 저장하지 않고,
세션 ID는 SHA-256 해시로만 저장한다. 경로는 `REDTEAM_LOG_PATH` 환경변수로
변경할 수 있다.

로컬 실행 모드:

```text
LOCAL_ENFORCEMENT_MODE=block_step_up_for_test
```

이 모드는 운영 정책이 아니라 레드팀 확인용이다. `recommended_action`이
`step_up` 또는 `step_up_and_rate_limit`이면 프록시가 메인 CAPTCHA 검증
요청을 전달하지 않고 로컬 차단 응답을 반환한다.

## 3. 현재 모델과 판정 기준

| 항목 | 값 |
|---|---|
| 모델 | `lightgbm_general_dynamics_min_fusion` |
| 모델 버전 | `revalidation_two_view_participant_safe_20260722` |
| Feature schema | `2.3` |
| 기본 Human 임계값 | `0.9999500521595306` |
| Step-up 해제 임계값 | `0.9999955746270602` |
| Medium risk 시작점 | `40` |
| High risk 시작점 | `70` |

주요 판정:

- Human score가 기본 임계값 미만이면 `ml_bot_score`
- 기본 임계값 이상이지만 step-up 해제 임계값 미만이면 `ml_step_up_band`
- 서버가 기록한 문제 발급·제출 시각 밖의 이벤트면
  `invalid_event_telemetry`로 최소 `step_up`
- 현재 로컬 테스트에서는 두 경우 모두 최종 통과하지 못함
- 화면의 Human 값은 소수점 셋째 자리까지만 표시되므로 `1.000`이어도 실제
  값이 step-up 해제 임계값보다 낮을 수 있음

## 5. 현재까지 확인한 핵심

1. 단순 직선과 단순 곡선 자동화는 현재 모델이 강하게 탐지한다.
2. 약 20점의 부드러운 곡선과 끝점 보정을 사용한 시도 C는 모델 점수를
   사실상 사람 수준까지 올렸다.
3. 시도 C가 최종 통과하지 못한 이유는 다른 고급 신호가 아니라
   `ml_step_up_band` 하나였다.
4. 화면 반올림 값만 보면 Human `1.000`으로 보이지만 실제 값은
   `0.999955`이므로 반드시 원본 점수를 함께 기록해야 한다.
5. 30점 S자형처럼 복잡성을 무작정 높이는 전략은 성능을 악화시켰다.
6. 현재 모델의 약점 후보는 "적당한 수의 점으로 만든 부드러운 곡선과
   작은 끝점 보정"이다.
7. 20점 곡선의 높은 사람 점수는 다른 문제에서 동일하게 재현되지 않았으며,
   문제의 이동 방향과 거리에 대한 민감도가 존재한다.
8. 프론트는 `pointer_move`를 약 40ms 간격으로 제한하므로 입력 경로의 점을
   늘려도 실제 모델 표본 수가 같은 비율로 증가하지 않는다.
9. 드래그가 이미지 영역을 벗어나 오른쪽 정답존으로 이동하면 정규화 `x`가
   `1.0`으로 고정된다. 시도 F에서는 마지막 네 이동점의 `x=1.0`이어서
   정답존 접근 구간의 수평 형태 정보가 손실됐다.
10. 고정 레드팀 후보를 브라우저 이벤트 대신 제출하면 정답과 행동 AI
    `allow`가 동시에 성립하므로 실제 우회 취약점이 존재했다.
11. 해당 우회의 직접 원인은 클라이언트가 보낸 행동 이벤트의 출처와 시각을
    서버가 검증하지 않았다는 점이다.
12. 서버 시간 바인딩 후 같은 상대시각 후보는 모델 점수와 관계없이
    `invalid_event_telemetry`로 `step_up` 처리된다.

## 6. 적용한 보완

### 6.1 CAPTCHA 서버의 신뢰 시각 전달

`ai-service-ms-behavior` 연동 계층에서 다음 시각을 행동 API에 전달한다.

- `presented_at`: DB에 저장된 challenge `created_at`
- `submitted_at`: verify 요청을 서버가 실제로 받은 시각

브라우저가 이 두 값을 정하지 않으며, 기존 세션 ID·challenge ID와 함께
행동 요청에 묶인다.

### 6.2 행동 API의 이벤트 시간창 검증

온라인 예측 API는 첫 이벤트와 마지막 이벤트가 서버가 기록한 문제 수명
안에 있는지 확인한다. 허용 오차는 현재 `5,000ms`다.

- 이벤트가 문제 발급 전이거나 제출 후이면 거부
- 이벤트 자체 지속 시간이 서버 관측 시간보다 길면 거부
- 서버 발급·제출 시각이 누락된 온라인 예측 요청도 거부
- 학습 수집 API는 기존 상대시각 데이터를 보존하기 위해 이 강제 검사를
  적용하지 않음

### 6.3 품질 거부와 위험 점수 결합

이전에는 품질 검사에서 `rejected`여도 모델 점수가 높으면 `allow`가 가능했다.
이제 온라인 예측에서 품질 거부가 발생하면:

- 이유에 `invalid_event_telemetry` 추가
- 위험 점수를 최소 `medium`으로 보정
- 권고 동작을 최소 `step_up`으로 제한

### 6.4 단순 프레임 규칙을 채택하지 않은 이유

최고 후보는 시간 간격 중복 비율이 높지만, 이 값만으로 차단하면 정상
사용자 오탐이 너무 커졌다.

| 규칙 | 정상 사용자 FRR | 레드팀 후보 탐지율 |
|---|---:|---:|
| 이벤트 40개 이상 + 중복 간격 0.90 이상 | `29.88%` | `79.78%` |
| 이벤트 40개 이상 + 중복 간격 0.95 이상 | `4.05%` | `43.82%` |

정상 사용자 FRR 목표 `3% 이하`를 만족하지 못하므로 이 규칙을 운영 차단에
사용하지 않았다.

### 6.5 자동 테스트 결과

- 행동 AI 전체 테스트: `183 passed`
- CAPTCHA 행동 연동 테스트: `6 passed`
- 추가 확인:
  - 서버 시간창 안의 절대시각 이벤트는 `valid`
  - 상대시각 또는 오래된 이벤트는 `rejected`
  - 서버 시각이 누락된 온라인 검증도 `rejected`
  - 품질이 거부된 고득점 모델 결과도 `allow`가 아닌 `step_up`

## 7. CAPTCHA UI에서 발견한 별도 결함

다음 문제는 행동 AI 점수와 별개로 메인 CAPTCHA 사용성과 데이터 품질에
영향을 준다.

### 레터박스 이미지와 드래그 영역 불일치

- 세로 사진이 가로 stage 안에 표시될 때 실제 이미지 양쪽에 빈 영역이 생김
- 객체 hit region은 stage 전체 비율로 배치되어 화면의 객체와 어긋남
- 화면에서 자전거를 탄 사람을 잡았지만 선택되지 않거나 다른 사람이 선택됨
- 빨간 반바지 사람을 잡았지만 검은 반바지 사람이 선택됨
- 두 시도는 정답이 보장되지 않아 행동 AI 검증에는 제출하지 않음

영향:

- 정상 사용자가 오답 객체를 선택하게 되어 CAPTCHA 정답률이 낮아짐
- 잘못된 객체를 다시 잡는 행동이 봇 feature로 오인될 수 있음
- 행동 데이터 라벨 품질이 나빠져 모델 검증을 오염시킴

보완 방향:

- 이미지가 실제로 그려진 content box 기준으로 hit region을 변환
- `object-fit: contain`의 좌우 또는 상하 여백을 좌표 계산에 반영
- 다양한 종횡비에서 bbox 시각 회귀 테스트 추가

## 8. 보안 관점의 판단

시도 H에서 실제 정답 검증과 행동 AI `allow`를 동시에 통과했다. 따라서
보완 전 상태는 배포 가능한 방어 완료 상태가 아니었다.

이번 서버 시간 바인딩은 확인된 고정 후보를 실제 종단간 테스트에서도
`step_up`으로 바꿨지만 완전한 행동 출처 증명은 아니다. 공격자가 이벤트
시각을 현재 challenge 시간창에
맞춰 다시 작성하면 클라이언트 제출형 API만으로는 진위를 확정할 수 없다.
브라우저 안에 넣은 서명 키도 공격자에게 노출되므로 해결책이 되지 않는다.

또한 현재 로컬 차단은 `step_up`을 강제로 실패 처리한 결과다. 운영 환경에서
`step_up`이 추가 CAPTCHA만 요청하도록 구성되면 자동화가 다음 문제를 계속
풀 수 있으므로, 반복 시도 제한과 세션 단위 위험 누적이 함께 필요하다.

최종적으로는 서버가 이벤트를 제출 시점에 한꺼번에 받는 방식이 아니라,
수집 중에 순서와 도착 시각을 직접 기록해야 한다. 모델 점수는 이 신뢰 가능한
프로토콜 신호와 결합할 때만 운영 차단 근거로 사용할 수 있다.

상세 구현 계약은 `docs/BEHAVIOR_EVENT_TRUST_PROTOCOL.md`에 기록했다.

  false`라 재생 탐지(DTW/exact-replay)는 불활성이었으나, 서로 다른 사람
  녹화본을 각 1회 제출하면 그 방어도 무력하다.

**공격 2 — 블랙박스 hill-climbing (질의 접근만)**

- 방법: weakset·사람데이터 없이, 직선 봇에서 출발해 궤적 knob(점수·곡률·
  시간·jitter·정지·보정)을 변이시키며 `human_score`가 오르면 채택. 400 질의.
- 결과: **미발견**. `human_score`가 파라미터형 봇 구간 전체에서 `0.0`으로
  포화되어 기울기가 없어 검색이 진행되지 않음.
- 해석: 순진한 파라미터 검색으로는 못 뚫는다(약한 희소식). 그러나 이는
  견고함이 아니라, 사람 manifold에 도달하려면 weakset처럼 **사람 분포에
  적합된 생성기**(PCA/GMM 등, `tools/redteam_weakness_search.py`)가 필요함을
  뜻한다. 공격 1·3이 그 경로를 이미 보여준다.

**공격 3 — 단일 씨앗 변종 공장**

- 방법: 통과 후보 1건(`...004442`)에 좌표 jitter / 이벤트 드롭 / 시간
  리스케일 / 공간 스케일 / 평행이동 / 복합 섭동을 각 30회 적용, 변종의
  allow율 측정.

| 섭동 | allow율 |
|---|---|
| 시간 리스케일 | 30/30 (100%) |
| 공간 스케일 | 30/30 (100%) |
| 평행이동 | 30/30 (100%) |
| 복합(시간+좌표) | 30/30 (100%) |
| 좌표 jitter(σ3px) | 27/30 (90%) |
| 이벤트 드롭(15~40%) | 19/30 (63%) |
| **종합** | **166/180 = 92.2%** |

- 해석: 통과 궤적 1개에서 DTW상 서로 다른 변종을 92% 성공률로 대량 생성할
  수 있다. 즉 재생/DTW 탐지를 넣어도 "하나의 녹화 → 무한 변종"으로 우회된다.
  좌표를 흔들거나 일부 이벤트를 버려도 대체로 통과가 유지된다.

**레드팀 종합**: 방어의 실패 지점은 모델 정확도가 아니라 **입력 신뢰**다.
(1) 사람 녹화본 재생 97.5%, (3) 그 씨앗의 변종 92% — 두 결과가 "record once,
mutate, replay"가 완전한 우회 경로임을 보여준다. (2)는 그 경로가 사람 분포
기반 생성에서만 열린다는 방향을 확인해 준다. 결론적으로 서버가 이벤트의
출처를 증명하지 못하는 한(11.4), 모델·임계값·정책모드 어떤 조정으로도
닫히지 않는다.

#### J-5. 방어 라운드 — 전송 타이밍 결속 프로토타입

레드팀 3종(J-3red)이 다 통했으므로 방어를 만들어 같은 공격으로 재검증했다.
계약서 §6의 "검증 직전 일괄 도착" 신호를 순수 함수로 프로토타이핑
(`tools/delivery_binding.py`). 서버가 수집 중 기록하는 배치별
`server_received_at`과 각 배치의 클라이언트 `t_ms`만으로, 이벤트가
자기 타임라인에 맞게 점진적으로 도착했는지 검사한다(궤적이 사람인지는 보지
않는다). 회귀 테스트 6건 통과(`tests/test_delivery_binding.py`).

전송 방식을 시뮬레이션해 loop 재검증(사람 120, weakset 89, 변종 60):

| 대상 / 전송 | 차단율 | 판정 |
|---|---|---|
| 정상 사람 · 정직한 스트리밍 (FRR) | 1.7% | ✅ 목표 3% 이하 |
| weakset · 버스트/빠른청크 | 100% | ✅ |
| 변종(공격3) · 버스트/빠른청크 | 100% | ✅ |
| 사람 재생(공격1) · 버스트/빠른청크 | 85.8% | △ 부분 |
| 사람 재생(공격1) · 페이싱 재생 | 1.7% | ❌ 우회 |
| 변종(공격3) · 페이싱 재생 | 0% | ❌ 우회 |

해석:

- **닫힌 것**: 미리 만든 궤적을 검증 직전 한꺼번에/빠르게 던지는 값싼 재생은
  weakset·변종에서 100% 차단되고 FRR은 1.7%다. 모델이 human 1.0을 줘도
  전송 형태가 프로토콜 위반이면 `step_up`으로 내려간다.
- **잔존 구멍 1 (짧은 드래그 면제)**: client 타임라인이 `800ms` 미만이면
  스트리밍할 것이 없어 버스트 검사를 면제한다. 이 면제가 FRR을 12.5%→1.7%로
  낮추지만, 사람 궤적의 `14.2%`가 800ms 미만이므로 **그 짧은 녹화본을
  버스트로 재생하면 이 층을 통과**한다. 공격1의 미차단 14.2%가 이것이다.
- **잔존 구멍 2 (페이싱 재생)**: 공격자가 원본 페이싱대로 실시간 재생하면
  전송 형태가 정직한 스트리밍과 구분되지 않아 통과한다(계약서 §1이 예고한
  한계). 변종 페이싱 재생 0% 차단이 이를 보여준다.

결론: 전송 타이밍 결속은 **낮은 FRR(1.7%)로 값싼 일괄 재생을 닫는 강한
1차 방어층**이지만, 단독으로는 짧은 녹화 재생과 페이싱 재생을 못 막는다.
계약서가 §3~6을 함께 요구하는 이유가 여기서 실증된다 — 전송 타이밍
신호만으로는 부족하고, **배치별 서버 sequence + 일회성 nonce/receipt
chain**과 결합해야 두 잔존 구멍이 닫힌다. 다음 라운드는 이 결합 방어를
프로토타이핑해 같은 6개 공격 회귀(계약서 §8)로 재검증하는 것이다.

이 프로토타입은 아직 온라인 예측 경로에 연결하지 않았다(수집 전송 계층이
없어 배치 도착 메타데이터가 API에 도달하지 않는다). 설계와 검증된 임계값을
모듈·테스트로 고정해 두었고, 전송 계층 구현 후 연결한다.

#### J-6. 방어 라운드 2 — nonce + receipt chain + delivery (결합)

R1 잔존 구멍을 공략하려 계약서 §3~4를 프로토타이핑
(`tools/receipt_chain.py`). 일회성 nonce가 체인을 시작하고, 각 배치는 직전
서버 발급 receipt(HMAC, 브라우저가 위조 불가)와 다음 sequence를 지녀야 하며,
verify는 nonce를 정확히 1회 소비한다. R1의 delivery_binding과 결합.

공격 재검증(사람 120, 짧은 사람 16):

| 대상 / 공격 | 통과율(PASS=우회) | 판정 |
|---|---|---|
| 정상 사람 (FRR) | 117/120 통과 (FRR 2.5%) | ✅ |
| receipt 재사용 | 0/120 | ✅ 차단 |
| sequence gap | 0/120 | ✅ 차단 |
| 이중 verify (nonce 재사용) | 0/30 | ✅ 차단 |
| 긴 궤적 fast-chunk 재생 | 16/120(짧은것만) | ✅ 긴것 100%차단 |
| 긴 궤적 burst 재생 | 16/120(짧은것만) | ✅ 긴것 100%차단 |
| **짧은녹화(<800ms) burst** | **16/16** | ❌ 근본한계 |
| **페이싱 실시간 재생** | **117/120** | ❌ 근본한계 |

해석:

- **닫힌 것**: 프로토콜 무결성 공격(receipt 위조/재사용, sequence 조작,
  verify 재생)이 100% 차단된다. 이는 "체인을 위조하거나 검증을 재생하는"
  공격을 완전히 막는 실질적 성과다. 대량 오프라인 재생(긴 궤적 버스트/빠른
  전송)도 delivery_binding이 100% 차단한다. FRR 2.5%로 목표 이하.
- **FRR 회귀 교훈**: 처음에 서버 도착 최소 간격(min_gap 40ms) 규칙을
  추가했더니 FRR이 35%로 폭증했다(정상 사람 39명 오탐). iter1의 "거친
  반응 규칙이 FRR을 파괴한다"를 재확인하고 제거했다. delivery_binding의
  비율·상관 검사만으로 충분하다.

- **근본 한계 (수정하지 않고 기록만 함)**: 다음 둘은 클라이언트 제출형
  프로토콜의 본질적 한계이며, 억지 규칙으로 막으면 FRR만 악화된다.
  1. **짧은 녹화 재생**: `800ms` 미만 사람 드래그(사람의 14.2%)는 스트리밍할
     것이 없어 delivery 검사가 면제되고, receipt chain은 무결하므로 통과한다.
     그 짧은 녹화본을 버스트로 재생하면 막을 수 없다.
  2. **페이싱 실시간 재생**: 공격자가 유효한 체인으로 원본 페이싱대로 실시간
     전송하면, 서버 관점에서 진짜 사람과 구분되지 않아 통과한다.
  두 경우 모두 "진짜 사람 궤적을 라이브처럼 전달"이므로 프로토콜 계층에서는
  구분 불가다. 계약서 §1이 예고한 한계가 실증되었다. 완전 차단은 클라이언트가
  오프라인으로 재현할 수 없는 신호(수집 중 서버가 주입하는 실시간 challenge
  nonce, 클라이언트 attestation 등)를 요구하며, 계약서 §8도 완전 증명은
  클라이언트 측만으로 불가능하다고 명시한다. 본 프로젝트 범위에서는 이 둘을
  **알려진 잔존 위험으로 문서화**하고, 세션 위험 누적·시도 제한·요청 빈도
  제한(운영 정책)으로 반복 악용 비용을 높이는 것으로 대응한다.

회귀 테스트 13건 통과(`tests/test_receipt_chain.py`,
`tests/test_delivery_binding.py`). 온라인 경로 미연결(전송 계층 부재).

#### J-7. 공격 라운드 3 — 시간창 tolerance 정밀 (온라인 경로)

커밋된 하드닝의 시간창 검증(조건3: `event_duration <= server_window +
5000ms`)을 실제 `/predict`로 정밀 스윕.

- 4032ms 후보: 서버창을 `0ms`(사람이 즉시 답했다고 주장)로 줘도 **allow**.
  tolerance(5000ms)가 후보 지속보다 커서 조건3이 통째로 삼켜진다.
- 12880ms 후보: 서버창 `7880ms` 미만이면 `invalid_event_telemetry`로 차단,
  `8880ms`(=D-4000, tolerance 안)부터 텔레메트리 통과. 경계가 정확히
  `D-5000`에서 형성됨(예측과 일치).

해석: 시간창 검증의 실제 정체는 "공격자가 제출 전 `(D-5000)ms`만 대기하면
된다"는 **대기시간 제약**일 뿐이다. 5초 미만 궤적(사람형 드래그 대부분)은
대기 0으로 무력화된다. tolerance를 줄여도 공격자는 더 오래 대기하면 되고
정상 사용자 시계 오차로 FRR만 악화되므로, 이 검사는 배치 전송 프로토콜(J-6)
없이 독립적으로 강화할 수 없다. **근본 한계로 기록만 함(수정 안 함).**
J-6의 결론(서버가 도착 시각을 직접 기록해야 함)을 재확인한다.

#### J-8. 분석 라운드 4 — 안전한 단일 특징 gate 존재성

모델 계층에 값싼 tell이 있는지(iter1 재검증). retimed-allow evader 36건 vs
실제 사람 400건을 9개 강건 특징으로 비교, FRR<3%에서 최대 탐지율 측정.

| 특징 | evader 중앙 | 사람 중앙 | 최대탐지@FRR<3% |
|---|---|---|---|
| vel_cv (속도변동성) | 2.715 | 1.349 | **63.9%** |
| mean_dt | 52.6 | 32.2 | 8.3% |
| n_events | 117 | 132 | 5.6% |
| path_per_event | 7.6 | 10.2 | 5.6% |
| duration/straightness/dt_cv/frac_x1/frac_round | — | — | 0.0% |

해석: 대부분 특징은 FRR<3%에서 사실상 분리 불가(0~8%)로 iter1의 "값싼 tell
없음"을 확인한다. 유일한 신호 `vel_cv`(evader가 더 jerky)조차 함정이다 —
그것은 이 PCA/GMM **생성기의 특성**이지 "재생 공격 일반"의 특성이 아니다.
공격 1(사람 녹화 재생 97.5%)은 사람의 vel_cv를 그대로 지니므로 이 gate를
통과하고, 36건에 맞춘 임계값은 알려진 weakset 과적합이다. **결론: 모델 특징
계층 방어는 생성기 두더지잡기이며 재생 공격을 못 막는다. 방어는 입력 신뢰
계층(J-6 프로토콜)이어야 한다.** 이 특징들을 검출기 학습·임계값 튜닝에
투입하지 않는다(규율 유지).

#### J-9. 분석 라운드 5 — 페이싱 재생 비용 정량

J-6 잔존 구멍 2(페이싱 재생)가 얼마나 값싼지 측정. 공격자가 배치 도착
타이밍을 녹화 대비 ±jitter로 재현할 때 delivery-binding 탐지율:

| 배치 도착 지터 ±ms | 탐지율 |
|---|---|
| 0 ~ 400 | 1.7% (=FRR 기저, 우회) |
| 800 | 10.8% |
| 1500 | 35.8% |
| 3000 | 70.8% |

해석: 공격자가 페이싱을 `±400ms` 안에 재현하면 우회한다(자동 재생기 `sleep`
수준, 저비용). 이 여유는 조일 수 없다 — 정상 사용자도 같은 전달 지터를 갖기
때문(±0에서도 FRR 1.7%). 페이싱 재생은 **저비용 잔존 위협**이고
delivery-binding을 과대평가하면 안 된다. 서버 주입 실시간 신호로만 닫힌다.

#### J-10. 분석 라운드 6 — 세션 히스토리 재생 탐지 커버리지

이번 세션 내내 비활성이던 `replay_detector.py`(DTW+exact fingerprint, MySQL
꺼짐)를 직접 단위로 검사. 라이브 DTW 임계값 `0.996693` 기준.

| 공격 | DTW 유사도 | 탐지 |
|---|---|---|
| 변종: translate | 1.000000 | ✅ 100% |
| 변종: scale | 1.000000 | ✅ 100% |
| 변종: coord_jitter σ3px | 0.952813 | ❌ 0% |
| 동일 녹화 재제출 | fingerprint 일치 | ✅ exact_replay |
| 서로 다른 사람 녹화 각 1회 | 0.972(평균 최대) | ❌ 미탐 |

해석: 재생 탐지 계층은 실질 커버리지가 있다 — literal 재생(fingerprint)과
translate/scale 변종(DTW가 min-max 정규화로 상쇄)을 잡는다. 그러나 **좌표
지터(σ3px)는 유사도 0.953으로 임계값 아래라 우회**하고, 서로 다른 녹화를 각
1회씩 쓰면 상호 유사도가 낮아 미탐이다. 임계값을 0.95로 낮춰 지터를 잡으려
하면 서로 다른 정상 사용자쌍(평균 최대 유사도 0.972)이 대량 오탐되므로 **낮출
수 없다**. 즉 이 계층은 값싼 반복 재생을 막지만, 지터 변종·녹화 로테이션은
못 막는다.

**행동 지침**: 이 계층은 현재 MySQL 미설정으로 완전 비활성이다(J-6 배포
정찰). `.env`에 MySQL을 설정해 세션 히스토리를 켜면, 추가 비용 없이 literal
재생·translate/scale 변종 커버리지가 즉시 활성화된다 — 연동 시 우선 조치.

#### 방어 계층 종합 (J 라운드 전체)

| 계층 | 막는 것 | 못 막는 것 |
|---|---|---|
| 모델(two-view) | 손제작 봇 | 사람형 궤적(재생·생성) |
| 시간창 검증(J-7) | 창 밖 시각 | 창 안 재생(대기만 하면) |
| 전송 결속(J-5) | 버스트/빠른전송 | 페이싱 재생(±400ms) |
| receipt chain(J-6) | 체인위조·재사용·seq | 유효체인 재생 |
| 재생탐지 DTW(J-10) | literal·translate·scale 반복 | 지터변종·녹화로테이션 |
| 특징 gate(J-8) | (안전한 것 없음) | — |

교차 생존(모든 계층 통과) 공격 = **페이싱 전송 + 좌표지터/개별녹화**. 이것이
클라이언트 제출형 프로토콜의 최종 잔존 위협이며, 서버 주입 실시간 신호로만
닫힌다. 운영에서는 세션 위험 누적·시도 제한으로 반복 비용을 높인다.

#### J-11. 방어 라운드 7 — risk_fusion end-to-end + 세션속도 결함 수정

실제 `fuse_behavior_risk` + `compute_replay_features`로 end-to-end 검증
(내 sketch 아님). 세 발견:

1. **교차 생존 공격 실제 확인**: 좌표지터 변종(path_sim=0.9938, 임계 0.9967
   바로 아래) + 세션 히스토리 → `allow risk=0.0`. exact=False(지터가
   fingerprint 변경). 실코드로 잔존 위협 재현.

2. **🔴 실제 결함 발견·수정**: `session_rate_exceeded`가 20/min에서 발동해도
   action이 `allow`였다. `session_rate_weight=30` < `medium_threshold=40`이라
   속도 신호 단독으론 step_up에 못 미쳤다. 공격자가 분당 30회 사람점수 재생을
   퍼부어도 전부 통과(reason만 로그). **수정**: 속도 초과 시 최소 medium으로
   floor(`risk_fusion.py`). 사람은 분당 20회 CAPTCHA를 풀지 않으므로 FRR
   안전. 수정 후 20+/min → `step_up`. 회귀 테스트 추가(201 passed).

3. **미사용 신호 정당성 확인**: `repeated_endpoint_count`/`repeated_duration_
   count`는 계산되나 fusion 미사용. 서로 다른 사람의 **88.7%가 끝점을 공유**
   (고정 정답존 탓, tol 0.01)하므로 endpoint 신호는 FRR 위험 — 미사용이 옳다.
   duration은 세션 내부 비교라 정상 사용자 본인의 몇 회 시도는 2ms 내 충돌이
   ~0이지만(전역 풀 38% 충돌은 생일역설 아티팩트), 공격자가 duration에 ±5ms만
   넣으면 무력화되는 **두더지잡기 신호**다. session-rate(속도는 못 속임)와 달리
   견고하지 않으므로 미사용이 옳다 — 반응적 규칙 남발을 피하는 규율(iter1).

이 라운드는 근본 한계가 아니라 **가중치 결함을 발견해 실배포 경로(risk_
fusion)에 반영**한 사례다. 세션 속도 제한이 이제 실제로 동작한다 — 반복
재생·변종 공장의 운영 비용을 높이는 실질 방어.

#### J-12. 공격 라운드 8 — 입력 강건성/자원 (새 공격 클래스)

재생이 아니라 "채점기를 깨거나 마비시키기". malformed·pathological 입력으로
예외→fail-open(allow) 또는 DoS가 가능한지 검사.

| 입력 | 결과 |
|---|---|
| 빈 배열 / 타입오염(x=str,y=None) | 422 (스키마 거부) ✅ |
| 좌표 전부 동일(분산0), 길이0 | step_up ✅ |
| 극단 좌표 1e9, 좌표에 NaN 삽입 | step_up (크래시 없음) ✅ |
| t_ms 역행·음수 | step_up ✅ |
| 초대량 이벤트 2k/20k/100k | 200, **크기 상한 없음** ⚠️ |

- **좋음(강건성 확인)**: 어떤 malformed 입력도 **allow로 fail-open되지 않고**
  예외 크래시(500)도 없다. NaN·극단값·역행시각 모두 안전 처리. 채점기가
  correctness 공격에는 강건함을 실증.
- **🟠 발견·수정한 결함**: `/predict`·`/collect`에 **이벤트 수/페이로드 상한이
  없었다**. 이벤트 10만개(18.7MB, 1.7초 CPU)가 그대로 수락됐다 — 봇이 대용량
  페이로드로 엔드포인트를 갉는 경미한 DoS 표면. **수정**: 스키마에
  `MAX_EVENTS_PER_ATTEMPT=5000` 상한 추가(`app/schemas/requests.py`). 사람
  최대가 ~1500이므로 3배 이상 여유 → 정상 드래그는 절대 거부 안 됨(FRR 안전),
  초과 페이로드는 채점 전 422. 회귀 테스트 추가(전체 201 passed).

이 라운드는 근본 한계가 아니라 **강건성 확인 + 실배포 경로의 자원 상한 결함
수정**이다.

#### J-13. 분석 라운드 9 — 클라이언트 자기신고 필드 조작

`predict.py`는 `payload.interaction`(regrab/retry/pointercancel/empty_click/
failed_drop)을 특징 추출기에 넘긴다. 이 값들은 브라우저(=공격자)가 자유롭게
설정하는 자기신고 필드다. 조작 표면인지 검사.

- 실측: 같은 궤적에 카운터를 clean(0)/messy(9)/extreme(9999)로 바꿔도
  `human_score` 불변(사람·우회후보 모두 1.0 고정).
- 번들 확인: 배포 two-view 모델의 **50개 feature에 interaction 카운터가 하나도
  없음.** 추출은 되지만 모델이 소비하지 않는다.
- 결론: **현재 조작 표면 아님(안전).** 승격된 two-view가 클라이언트 조작 가능
  필드를 올바르게 배제한 좋은 설계 속성.
- ⚠️ **가드레일**: 향후 모델 승격 때 interaction 카운터(또는 다른 클라이언트
  자기신고 값)를 온라인 모델 feature로 다시 넣으면 즉시 조작 표면이 된다.
  온라인 판정 feature는 서버가 관측·검증 가능한 신호로만 구성해야 한다.

#### J-14. 공격 라운드 10 — 궤적 변환 공격군 (기하/시간)

좌표지터(J-10)와 다른 축: 사람 녹화 하나를 기하·시간 변환해 변종 대량생산.
통과율 + 원본과의 DTW 유사도(재생탐지 회피 여부) 측정. 사람 40건 표본.

| 변환 | 모델 통과 | DTW 재생탐지 |
|---|---|---|
| timewarp ×2 (느리게) | 39/40 | 40/40 잡힘 (DTW 시간불변) |
| timewarp ×0.5 (빠르게) | 16/40 | 40/40 잡힘 |
| resample (점 절반) | 30/40 | 0/40 회피 |
| mirror (좌우반전) | 38/40 | 0/40 회피 |
| rotate 15° | 37/40 | 0/40 회피 |
| shuffle 중간점 | **2/40** | — |
| stitch (두 사람 절반) | 34/40 | 0/40 회피 |

발견:

1. **기하 변환(mirror/rotate/resample/stitch)이 모델과 DTW 재생탐지를 동시에
   우회한다.** DTW가 축별 min-max 정규화라 회전·반전은 완전히 다른 경로로 보여
   유사도가 임계 아래로 떨어진다. 사람 녹화 하나로 좌표지터보다 싸고 다양하게
   DTW상 구별되는 변종을 무한 생산할 수 있다.
2. ✅ **shuffle(중간점 순서 섞기)은 2/40만 통과** — 모델이 점 순서·궤적 일관성에
   민감하다는 좋은 성질. 무작위 재배열은 봇으로 잡힌다.
3. **순수 시간왜곡은 DTW가 잡는다**(시간불변). 재생탐지를 회피하는 것은 기하
   변환뿐이다.

보완 방향 (AI 단독 불가, 크로스서비스): mirror/rotate/stitch는 드래그 끝점·경로가
**실제 발급된 정답존 기하와 불일치**한다. 그러나 행동 AI는 궤적만 받고 문제의
target bbox를 모르므로 구조적으로 이를 검증할 수 없다. 해답은 캡차 계층의
**좌표-객체 끝점 결속**(`behavior_action_binding`, 계약서/§7·0727 문서 §4):
선택한 객체의 발급 bbox 안에서 시작하고 같은 객체의 drag→drop→selection 순서를
남겨야 통과. 이 검사가 있으면 기하 변환 변종은 끝점이 어긋나 걸린다. AI 코드
변경 없음 — 크로스서비스 방어 요구사항으로 기록.

#### J-15. 방어 라운드 11 — 세션 교체 재생 + 전역 fingerprint

공격: 재생탐지는 `recent_session_history(session_id=...)`로 **의도적으로 세션
스코프**다(다른 학생 궤적 오탐 방지). 그래서 공격자가 **매 시도 새 session_id**를
쓰면 히스토리가 비어 exact_replay·DTW가 전부 무력 — 동일 궤적도 무한 재생 가능.

보완(AI/백엔드측 신규 프로토타입 `tools/global_fingerprint.py`): DTW 유사도가
아니라 **정확한 path fingerprint(SHA-256)** 를 세션 무관 전역으로 짧게 추적
(TTL·용량 경계, 해시만 저장). 같은 exact 경로가 다른 세션에서 재등장하면
exact_replay로 step_up.

- **FRR 안전 실측**: 사람 3000명 exact-fingerprint 고유 3000개, **충돌 0건**.
  서로 다른 두 사람이 바이트 동일 경로를 만들 확률 ~0이므로 전역 exact-match는
  정상 사용자를 오탐하지 않는다.
- **프라이버시**: 세션·참여자 식별자 없이 경로 해시만 TTL 보관.
- **한계(설계상 의도)**: 기하 변환(mirror/rotate/resample)은 fingerprint가 바뀌어
  이 검사로는 안 잡힌다 — 그건 R14(J-14)의 캡차측 객체 결속 몫이다. 두 방어는
  상보적: 전역 fingerprint = literal 세션교체 재생, 객체 결속 = 기하 변환.
- 회귀 테스트 5건(용량 경계 버그 1건 발견·수정), 전체 207 passed. 온라인 경로
  미연결(공유 상태 저장소는 배포 시 DB/캐시로 뒷받침).

#### J-4. 라이브 CAPTCHA 화면 확인

- 프록시(`:18001`)를 통해 라이브 문제·실사진·정답 검증·shadow 점수 패널이
  모두 정상 로딩됨(`/api/captcha/assets/{id}/image` 200).
- 이 세션에서 정상 사용자 궤적(Human FRR) 실측은 아직 수집 전. 라이브 DB에
  기록이 남으므로 레드팀 궤적과 정상 궤적을 challenge ID로 분리 관리해야
  한다.

- 캡차 측 `BEHAVIOR_AI_URL` + `BEHAVIOR_EVENT_TRANSPORT=shadow`
  (`ms` 담당). `behavior_client`가 fail-open이라 AI 장애가 캡차 통과·실패를
  바꾸지 않는다.
- **목적**: 실제 사용자 궤적 + AI 점수 쌍 수집 → **Human FRR 최초 실측**.
  이것이 현재 최대 블로커의 해소 경로다.

### 11.4 근본 방어 (연동과 병행, 최대 작업)

- **이벤트 신뢰 프로토콜**(`docs/BEHAVIOR_EVENT_TRUST_PROTOCOL.md`):
  제출 시점 일괄 수신을 버리고, 수집 중 서버가 도착 시각·증가 sequence를
  직접 기록. retime 우회(J-2)의 근본 원인이 여기다. 백엔드 팀 협의 필요.
- **retimed holdout 고정화**: J-2의 89건 retimed 세트를
  `training_usage=external_holdout_only`로 봉인해 회귀 기준으로만 사용.
  학습·임계값 튜닝 금지(`training/holdout_registry.py`).

### 11.5 정책 승격 (지표 충족 후에만)

- 단계적: `low=allow` → `high=step_up+rate limit` → `medium=step_up`.
  `medium`을 마지막에 켠다(정상 사용자 다수가 이 구간).
- **`active` 승격은 retime 우회를 막지 못한다**: 통과 36건은 `step_up`이
  아니라 `allow`를 받으므로 정책 모드 변경으로 해결되지 않는다. 11.4가
  선행되어야 한다.
- `step_up`의 의미 정의 필요(추가 캡차 1회면 자동화가 계속 시도 가능).
  세션 위험 누적·시도 제한·성공무관 challenge 소비를 함께 검증.
- 승격 게이트: Human FRR ≤3%, 알려진 Bot ASR ≤5%, 미지 family 최악
  ASR ≤10%, AI 응답 p99 < 1.5s(타임아웃). 현재 모두 미실측 또는 미달.

## 10. 실험 기록 원칙

앞으로 각 시도에 다음 항목을 반드시 추가한다.

- 문제 문구와 정답 객체 수
- 궤적 유형과 점 개수
- 드래그 전 이동과 끝점 보정 여부
- Human score와 Bot risk score 원본 값
- Risk score, risk level, recommended action
- `reasons`
- 정답 성공 여부와 행동 AI 최종 통과 여부
- 이전 시도 대비 변화와 해석
