# 하지영님께 — 임계값 교정 (5절 답변)

보낸 사람: 조성원 · 2026-07-30

---

## 0. 먼저

머지·`record` 전환·시험 방어까지 하루에 정리해 주셔서 감사합니다. 특히 게이팅을 일부러
도로 빼서 새 테스트가 실제로 잡는지 확인하신 것, 그리고 시험 방어에서 **공격 자체를
재현하는 테스트**(`test_random_guessing_cannot_farm_completion`)를 만드신 것 — 둘 다
"통과했다"가 신호가 되게 만드는 방식이라 좋았습니다.

곁다리로 잡으신 버그 2건(429에 답이 날아가던 것, `detail` 객체로 React가 죽던 것)도
제가 만든 흐름에서 나온 것이라 잡아주셔서 다행입니다.

로컬 DB `bot_suspicion` 공유도 감사합니다. "ORM 컬럼 추가는 기능 플래그로 롤백할 수
없다"가 로컬에서도 똑같이 성립한다는 지적이 정확합니다.

## 1. 시나리오 방식에 동의합니다 — 다만 초점을 바꿔야 합니다

관측만으로는 0건을 며칠 뒤에 확인하는 일이 된다는 진단에 동의합니다. 제가 리뷰 2절에
쓴 말이 제 임계값에 그대로 돌아온 셈입니다.

다만 제안하신 6개 시나리오 중 **"명백한 자동화" 쪽은 돌려도 얻을 게 적습니다.**
position 건너뛰기가 +3을 만드는 건 코드를 읽으면 알 수 있고, 어차피 걸리라고 만든
경로입니다.

**정작 알아야 할 것은 반대쪽입니다** — 정상 학생이 우연히 신호를 밟는 경로가 있는가.
가중치가 틀렸다면 거기서 드러납니다.

---

## 2. 그리고 시나리오를 돌리기 전에 이미 하나 드러났습니다

### `SUSPICION_SESSION_CONFLICT = 5` 는 너무 큽니다

409가 나는 지점을 다시 봤습니다.

```python
if bump_suspicion(progress, SUSPICION_SESSION_CONFLICT, "session_conflict"):   # +5
    db.commit()
raise HTTPException(409, detail={"message": "...이어보기를 눌러 주세요.",
                                 "active_elsewhere": True})
```

**409는 "여기서 계속하기"를 누르기 전 단계에서 납니다.** 즉 정상적인 기기 이동 흐름이
이렇습니다.

```
다른 기기에서 열기  →  409 (+5)  →  "이어보기" 안내  →  누름  →  takeover (bump 없음)
```

`SESSION_TTL_SEC = 30`이라 **마지막 하트비트로부터 30초 안의 새로고침도 같은 경로**입니다.
30초를 넘기면 조용히 재점유되어 신호가 없습니다.

그리고 이건 제 추측이 아니라 **기존 코드가 이미 정상이라고 선언해 둔 동작**입니다.

```python
# takeover 상한 — 두 세션이 하트비트마다 번갈아 takeover하면 동시 재생 차단이 무력화되므로
# 별도의 낮은 상한을 둔다. 정상 사용(새로고침·기기 이동)은 시간당 수 회를 넘지 않는다.
RATE_TAKEOVER_PER_HOUR = 30
```

**"정상 사용은 시간당 수 회"** 인데, 그 수 회 중 **2회면 임계 10에 도달합니다.**
노트북 → 폰 → 노트북 한 번이면 끝입니다.

### 이건 시나리오로 발견할 게 아니라 이미 정해진 값입니다

`5 × 2 ≥ 10`은 관측이 필요 없습니다. **시나리오를 돌리면 "예상대로 걸렸다"를 확인할 뿐**이라,
이건 돌리기 전에 정하는 게 맞다고 봅니다.

### 제안 — 신호를 409가 아니라 takeover 빈도로

409 자체는 계정 공유의 신호가 아닙니다. **한 사람이 기기를 옮겨도 나옵니다.**
진짜 공유 신호는 **번갈아 takeover가 반복되는 패턴**이고, 그건 이미
`RATE_TAKEOVER_PER_HOUR`가 보고 있는 것과 같은 축입니다.

| 안 | 내용 | 평가 |
|---|---|---|
| **A** | `SUSPICION_SESSION_CONFLICT` 를 **5 → 2** | 즉시 적용 가능. 5회 누적해야 임계 — "시간당 수 회"와 겹치지 않음 |
| **B** | 409 에서 bump 하지 않고, **시간당 takeover 횟수가 정상 범위(예: 5회)를 넘을 때** bump | 원리적으로 맞음. 기기 이동과 공유를 실제로 구분 |
| **C** | 409 직후 같은 학생이 N초 안에 takeover 하면 **bump 취소** | 한 사람이 옮긴 것이 증명되므로. 구현은 A·B보다 번거로움 |

**A를 지금 적용하고, B를 다음 단계로** 두는 걸 권합니다. A는 한 줄이고 되돌리기 쉽습니다.
B는 상태를 하나 더 봐야 해서 시험 방어처럼 따로 잡는 게 낫습니다.

### 체크포인트 쪽도 비슷한 의심이 있습니다

`SUSPICION_CHECKPOINT_EXHAUSTED = 4`, `MAX_CHECKPOINT_FAILS = 3`.
**캡차를 진짜로 3번 연속 틀리는 학생**이 +4를 받습니다. 두 번 겪으면 8입니다.
여기에 기기 이동 한 번(현재 +5)이면 13 — 임계 초과입니다.

이건 값을 재봐야 압니다. 아래 시나리오 5번이 그 답을 줍니다.

## 3. 수정한 시나리오 표

제안하신 6개를 기준으로, **정상 쪽을 늘리고 자동화 쪽을 줄였습니다.**

### A군 — 정상인데 신호를 밟을 수 있는 경로 (여기가 핵심입니다)

| # | 시나리오 | 왜 보나 |
|---|---|---|
| A1 | **30초 안에 새로고침 2회** | 현재 설계로는 +10 = 임계 도달. **가장 먼저 봐야 합니다** |
| A2 | 노트북 → 폰 → 노트북 (이어보기 클릭 포함) | 실제 기기 이동의 총 비용 |
| A3 | 네트워크 끊김 30초 후 재접속 | TTL 경계에서 조용히 재점유되는지, 신호가 나는지 |
| A4 | 탭 백그라운드 / 절전 후 복귀 | wall-clock 은 흐르는데 하트비트가 끊긴 구간 |
| A5 | **체크포인트 캡차를 진짜로 3번 틀림** (2라운드) | +4 × 2 = 8. 못 푸는 학생이 임계에 닿는가 |
| A6 | 되감기 후 이미 본 구간을 빠르게 넘김 | `watched` 이하 이동이 위반으로 잡히지 않는지 |
| A7 | 정상 시청 40분 (1배속, 끝까지) | 감쇠가 이겨 0 근처를 유지하는가 |
| A8 | 2배속 시청 | `SPEED_FACTOR 2.5` 안이라 **안 걸려야** 정상 |

### B군 — 명백한 자동화 (하한 확인용, 최소만)

| # | 시나리오 | 기대 |
|---|---|---|
| B1 | position 건너뛰기 반복 | +3 누적, 5분 내 임계 초과 |
| B2 | 두 탭 진짜 동시 재생 (번갈아 takeover) | 임계 초과 |
| B3 | 재생 멈춘 채 하트비트만 | 감쇠가 걸리지 않아 값 유지 (전진 없는 비트는 감쇠 대상 아님) |

## 4. 어떤 값이 나오면 "맞다"고 볼 것인가

물어보신 부분입니다. **판정 기준을 미리 못박아 두는 게 맞습니다** — 나중에 숫자를 보고
기준을 만들면 그건 그냥 지금 값을 정당화하는 일이 됩니다.

```
합격 조건

  A1~A4 (정상 이상 상황)   각각 3회 반복해도  최종 의심도 < 5   (임계의 절반)
  A5    (못 푸는 학생)      2라운드 후          최종 의심도 < 10  (임계 미만)
  A7    (정상 장시간)       40분 후             최종 의심도 = 0
  A8    (2배속)            전 구간              신호 0건

  B1~B2 (명백한 자동화)    5분 이내            임계 10 초과
  B3                      감쇠 없음            값 유지
```

**A1이 떨어지면 나머지는 볼 필요 없습니다** — 가중치부터 고치고 다시 돌려야 합니다.
저는 현재 값(+5)으로는 A1이 떨어진다고 봅니다. 그래서 2절의 A안을 먼저 적용하고
시작하시길 권합니다.

**B군이 통과 못 하면** 임계가 너무 높은 것이니 반대로 내려야 합니다. 다만 B군은 통과할
것으로 봅니다 — 애초에 걸리라고 만든 경로입니다.

## 5. 역할 분담 — 제가 설계하고, 실행은 지영님께 부탁드립니다

물어보신 세 번째 선택지입니다.

- **설계·판정 기준**: 제가 냅니다. 3·4절이 그것이고, 추가할 게 있으면 말씀해 주세요.
  근거 없는 가중치를 정한 게 저라, 무엇이 나오면 틀린 건지도 제가 명시하는 게 맞습니다.
- **실행**: 지영님께 부탁드립니다. 로컬 환경과 프런트가 있으시고, 시험 방어에서 이미
  화면까지 확인하는 방식으로 검증하셨습니다. A1~A4는 **실제 브라우저 조작**이 필요해
  제가 할 수 없는 부분입니다.
- **해석**: 결과 나오면 같이 보겠습니다.

기록은 시나리오별로 `(최종 의심도, 신호 종류별 발생 횟수)` 정도면 충분합니다.
`bot_suspicion` 값과 `bot_suspicion +N (reason)` 로그 라인을 보시면 됩니다.

## 6. 한계는 그대로 남습니다

말씀하신 대로 이건 **저희가 만든 행동**이지 실제 학생 행동이 아닙니다. 시나리오가
말해주는 건 **"이 행동은 이만큼의 값을 만든다"**이지 **"정상 학생이 이 행동을 얼마나
자주 하는가"**가 아닙니다.

그래서 이렇게 정리하는 게 맞다고 봅니다.

```
시나리오로 정하는 것    가중치의 상대적 크기, 명백히 틀린 값 걸러내기
실사용으로 정하는 것    임계값의 절대 수준
```

`record`는 그대로 켜두고, 실사용이 늘면 그때 진짜 데이터로 임계값을 다시 봅니다.
그전까지는 **보수적으로**(잘 안 걸리는 쪽으로) 두는 게 맞습니다 — `enforce`에서 오탐의
대가가 "캡차 1회"라 해도, 안 걸려도 될 사람이 걸리는 건 여전히 비용입니다.
