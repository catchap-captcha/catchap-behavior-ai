# 드래그 단위 스코어링 — 두 기준을 동시에 만족하는 동작점이 처음 나왔다

조성원 · 2026-08-03

---

## 결론

메인 캡차 실데이터 411건에서, **세션 단위를 드래그 단위로 바꾸면 사람 FRR 1.5% ·
봇 ASR 0%** 가 된다. 7/31에 "어느 임계값에서도 두 기준을 동시에 만족하지 못한다"고
적었는데, **그건 세션 단위 안에서만 참이었다.**

| 스코어링 | 임계값 | 사람 FRR | 봇 ASR |
|---|---:|---:|---:|
| 세션 (현재) | 0.99995 | 16.4% | 14.2% |
| 세션 (최적) | 0.05 | 1.5% | **45.8%** |
| **드래그 중앙값** | **0.01** | **1.5%** | **2.0%** |
| 드래그 중앙값 + 최소이동 규칙 | 0.01 | **1.5%** | **0%** |

바뀐 것은 모델이 아니다. **같은 모델, 같은 특징, 입력 단위만 다르다.**

---

## 왜 이게 되나

기존 특징은 `event_count`·`duration_ms`·`total_distance` 같은 **세션 합계**다.
객체를 5번 끌면 전부 5배가 되고, 자로 그은 직선도 `1.0000` 을 받는다(7/31 측정).
공격자에게 "여러 번 끌기"는 반복문 한 줄이라 가장 싼 우회였다.

드래그마다 점수를 내면 그 지렛대가 사라진다. **직선 5개는 여전히 직선 5개다.**

그리고 세션 합계가 가리고 있던 것이 드러난다.

```
사람 드래그 2회 이상 56건
  세션 점수로는  53/56 통과
  드래그 min으로   4/56 통과
```

지금까지 다중 드래그 사람이 통과한 것은 **모델이 그들을 사람으로 알아봤기 때문이
아니라 합계가 부풀려졌기 때문**이었다. 통과율이 실력이 아니라 부산물이었다.

드래그 단위로 보면 분포가 훨씬 멀다.

```
드래그당 평균 점수    사람 0.97    봇 0.035
```

임계값 `0.99995` 는 이 분리를 못 쓴다. 너무 끝에 있어서 사람도 같이 자른다.
동작점을 옮기면 두 기준이 함께 만족된다.

---

## 남은 봇 5건은 전부 한 계열이었다

`threshold 0.01` 에서 통과한 봇 5건은 **전부 `teleport`** 다. 세션 단위에서도
0.994~0.997 로 통과하던 계열이라, 드래그 단위가 새로 만든 구멍이 아니다.

특징이 하나로 갈린다.

| | 드래그당 `pointermove` |
|---|---|
| teleport 봇 | **정확히 1** (5/5건) |
| 그 외 봇 | 최소 2 · 중앙 8 |
| 사람 | 최소 2.3 · 중앙 11 |

**드래그당 중간 이동이 2개 미만이면 사람의 드래그가 아니다.** 이 규칙 하나로 잔여
ASR이 0이 되고, 사람 쪽 비용은 없다(사람 최솟값이 2.3).

다만 이건 **한 계열에 맞춘 규칙**이다. 공격자가 이동을 2개로 늘리면 우회하고,
그때는 궤적 모델이 다시 본다. 하한선으로만 쓴다.

## 오탐 2건

```
sw-mouse  드래그 1회  중앙 0.000000
sw-mouse  드래그 1회  중앙 0.000009
```

둘 다 단일 드래그다. 드래그 단위 스코어링에서 단일 드래그 사용자는 표본이 하나뿐이라
운이 나쁘면 그대로 걸린다. **정답이 1개인 문항을 푸는 사람이 불리하다**는 7/31의
공정성 문제가 여기서도 그대로 남는다.

---

## 이 측정의 한계 — 작게 적지 않는다

**① 임계값 0.01을 이 데이터에서 골랐다.** 낙관 편향이 있다. 7/22에 hard-negative
후보가 OOF 2.39% → untouched test 9.06% 로 튀었던 것과 같은 함정이다. **밀봉
홀드아웃에서 한 번 채점하기 전까지 이 숫자는 후보값이다.**

**② 사람이 2명 134건이다.** FRR 1.5% 는 오탐 2건이라는 뜻이다. 승급 기준의
"사람 5명 전원" 은 그대로 미달이고, 이 수치의 정밀도도 낮다.

**③ 봇 253건은 전부 내 레드팀 도구다.** 드래그 단위로 채점된다는 걸 아는 공격자는
각 드래그를 사람처럼 만들 것이다. 그건 규모를 부풀리는 것보다 훨씬 비싸므로 이득은
실재하지만, **ASR 2%는 적응하지 않은 공격자 기준이다.**

**④ 499건 중 88건을 뺐다.** 운영이 기록한 점수를 우리 파이프라인이 재현하지 못한
행이다(재현율 82.4%, 중앙 오차 1.4e-5). 재현 안 되는 행은 입력이 다르다는 뜻이라
세션↔드래그 비교가 성립하지 않는다. **제외 사유는 아직 규명 못 했다.** 재현율을
올리는 것이 다음 작업 중 하나다.

---

## 재현율 82.4% — 원인 추적 결과 (미해결)

원인을 찾지 못했다. 배제한 것과 남은 것을 적는다.

**배제됨**

| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 이벤트 집합이 다르다 | `ai_attempt_features.pointer_event_count` vs 저장 행 수 | **499/499 일치** |
| 모델·임계값이 다르다 | `ai_model_predictions` 그룹핑 | 전부 동일 버전·임계값 |
| 예측 행이 여러 개다 | attempt별 예측 수 | 전부 1건 |
| `t_ms` 절대/상대 | 두 방식 모두 채점 | 결과 동일 (특징이 이동 불변) |
| `interaction` 인자 누락 | 해당 5개 카운터가 모델 특징에 있는지 | 모델은 안 씀 |
| 좌표 정밀도 손실 | 컬럼 타입 | 전부 `double` |
| viewport 폭 차이 | 그룹별 암묵적 폭 분포 | 두 그룹 유사 (500 우세) |

**좌표는 픽셀이 맞다.** 정규화로 바꾸면 재현율이 82.4% → 61.1% 로 떨어지고 중앙
오차가 1.4e-5 → 2.4e-3 으로 커진다. 측정으로 확인했다.

**결정적 시험이 실패한 이유.** 저장된 이벤트를 실행 중인 AI 서비스 `/predict` 에
그대로 다시 보내 봤는데, **로컬이 1e-5 로 재현한 행조차 재요청에서는 안 맞았다.**

```
[재현됨] 기록 0.000000  재요청 0.066871  불일치
[어긋남] 기록 0.917788  재요청 0.999376  불일치
```

즉 이 시험은 결론을 못 낸다. `/predict` 는 `captcha.width/height` 를 필수로 받는데
그 값이 저장돼 있지 않아 역산해서 넣었고, 그 추정이 틀리면 점수가 달라진다.
**원래 요청을 복원할 수 없는 것이 병목이다.**

**그래서 제안** — 예측 행에 **채점에 쓴 특징 벡터(또는 요청 본문의 해시)를 같이
남기자.** 지금은 "무엇을 채점했는가" 를 사후에 알 방법이 없어서, 이런 질문이 나올
때마다 추측하게 된다. 컬럼 하나면 이 질문은 영구히 한 번의 조회로 끝난다.
