# CatChap 행동 AI 레드팀 — 공격·보완 정리 (2026-07-27, 정정판)

> **정정 안내**: 이 문서의 이전 판은 "재생 우회 97.5%가 안 닫혔고 근본 방어는
> 미구현"이라고 적었으나 **이는 틀렸다.** 재생 방어(서버측 receipt-chain 배치
> 수집 프로토콜)는 팀이 이미 `ai-service-ms-behavior`에 구현했고 테스트로
> 검증돼 있다. 아래 §1이 팀의 원래 구현, §2가 이번 세션에 추가한 수정,
> §3이 정정 내용이다.

---

## 0. 무엇을 어떻게 테스트했나

- 행동 AI `/predict`에 오프라인으로 적대적 궤적을 제출하는 레드팀 14라운드.
- **주의(중요 전제)**: 이 공격은 `/predict`를 **백엔드 키로 직접** 호출했다.
  실제 브라우저 공격자는 이 경로에 닿을 수 없다 — AI는 `127.0.0.1:8010`
  내부 전용, 외부 방화벽 차단, `X-Captcha-Backend-Key` 필요. 실제 공격 경로는
  캡차 `verify`를 거치며, 그 계층에 §1의 방어가 있다.

## 1. 팀이 원래 구현한 방어 — 서버측 이벤트 신뢰 프로토콜 (핵심)

재생 공격("미리 만든 사람형 궤적을 검증 순간에 끼워넣기", 시도 H)의 **근본
해결**. `ai-service-ms-behavior`에 구현, 로컬 테스트 23개 통과. 계약은
`docs/BEHAVIOR_EVENT_TRUST_PROTOCOL.md`, 실험 기록은
`local-test-data/LOCAL_BEHAVIOR_SECURITY_TEST_2026-07-27.md`.

| 방어 | 구현 위치 | 하는 일 |
|---|---|---|
| **서버 저장 배치만 채점** | `verify` → `db.trusted_behavior_events` | verify가 브라우저가 보낸 `events`를 무시하고, 수집 중 서버가 저장한 receipt 검증 배치만 모델 입력으로 씀 → 미리 만든 궤적을 끼워넣을 수 없음 |
| **nonce + receipt chain + sequence** | `collect_behavior_batch` → `db.append_behavior_batch`, `_validate_behavior_batches` | 일회성 nonce로 체인 시작, 배치마다 HMAC receipt·payload_hash·순번 검증. 위조·재사용·순번 조작 거부 |
| **좌표-객체 결속** | `validate_behavior_action_binding` | press가 선택한 객체의 발급 hit region 안에서 시작하고 drag→drop→selection 순서를 남겨야 함. 객체 밖 시작 → `behavior_action_start_outside_source` |
| **lifecycle 검증** | `validate_behavior_lifecycle` | 제출 전 완전한 드래그 생명주기 요구 |
| **배치 전송 타이밍** | `detect_batch_delivery_timing` | 긴 궤적을 검증 직전 짧은 버스트로 업로드하면 탐지(서버 도착 간격 vs 클라 타임라인) |
| **stop-go / sparse-pause 신호** | `detect_stop_go_signal` | 스크립트성 정지→급출발→종점보정 패턴 탐지 |
| **정책 결합** | `resolve_final_verdict`, active 분기 | active 모드에서 위 신호가 걸리면 step_up 강제. shadow에서는 기록만 |

DB: `captcha_behavior_sessions`, `captcha_behavior_batches`(payload/receipt/
previous hash + server received_at).

**효과**: 시도 H(버스트 재생)는 이 프로토콜 적용 후 시도 I에서 `step_up`으로
막혔다(팀 문서 기록). 즉 end-to-end 재생 swap 공격은 닫혀 있다.

## 2. 이번 세션에 추가한 수정 (행동 AI 측, 보조)

레드팀 14라운드 중 발견한 **행동 AI(`ai-service`) 자체의 실제 결함 2건 수정 +
하드닝 반영**. §1의 캡차측 방어와 별개인 advisory/입력검증 계층.

| 수정 | 커밋 | 내용 | 상태 |
|---|---|---|---|
| 하드닝 | `74ec5e7` | 온라인 `/predict` 서버 시간창 검증 + 품질거부 시 고득점이어도 step_up 상한 | **GPU AI 배포본 반영·재시작·동작확인 완료** |
| 세션속도 결함 (R8) | `103afe2` | `session_rate_exceeded`가 20/min에서 발동해도 action=allow였음(가중치 30<medium 40). medium floor로 수정 | 로컬 커밋(하드닝과 함께 배포본에도 반영됨) |
| 이벤트 상한 (R10) | `0d8e9fa` | `/predict`·`/collect`에 이벤트 수 상한 없어 10만개(18.7MB) 수락 → `MAX_EVENTS_PER_ATTEMPT=5000` | 로컬 커밋, 배포 schema 업로드(재시작 대기) |

**중복 고지(정직)**: 이번에 `tools/`에 만든 프로토타입 4종(delivery_binding,
receipt_chain, online_policy_sketch, global_fingerprint)은 §1의 캡차측 방어와
**기능이 겹친다.** 고립된 AI만 보고 재발명한 것으로, 새 방어가 아니라 §1의
개념 검증·회귀 자료로만 의미가 있다.

## 3. 정정: 97.5% 재생 우회의 진짜 의미

- **잘못 말한 것**: "재생 97.5%가 안 닫혔다 / 근본 방어 미구현 / 범위 밖".
- **사실**: 97.5%는 **행동 AI 모델 단독**이 재생된 사람 궤적을 "사람"으로
  판정하는 비율이다. 이는 모델의 맹점이 맞지만 **end-to-end 우회율이 아니다.**
  실제 흐름은 §1의 서버측 프로토콜을 거치며, 거기서 버스트 업로드·객체 밖
  시작·순번/영수증 위조가 차단된다.
- **모델과 시스템을 혼동**했다. 모델은 재생을 못 가르지만, 시스템은 입력 신뢰
  계층(프로토콜)에서 막는다.

### 정정된 위협 그림

```
브라우저 공격자
  → 행동 AI :8010 직접 불가 (내부전용+방화벽+백엔드키)
  → 캡차 verify 경유 필수
      → 서버 저장 receipt-chain 배치만 채점 (미리만든 궤적 끼움 불가)
      → 버스트 업로드 탐지, 객체 밖 시작 거부, 순번/영수증 위조 거부
  → 남는 좁은 잔존: 녹화 궤적을 올바른 페이스로 receipt-chain 배치 스트리밍 +
     정답 객체 hit region에서 시작까지 완벽 재현 (고비용, 계약서 §1 인정 한계)
```

## 4. 여전히 유효한 결과 (정정 후에도 사실)

- 손제작 봇 16종 + 합성 봇 → 모델이 0% 통과(강함).
- 입력 강건성: malformed(NaN·극단·역행) fail-open/크래시 없음.
- 클라 자기신고 `interaction` 카운터는 배포 two-view 모델 feature 미포함(조작 불가).
- 범위 밖 좌표는 품질검증이 `invalid_event_telemetry`로 차단.
- 모델 특징 계층엔 안전한 단일 gate 없음(재학습·튜닝으로 재생 못 막음) — 그래서
  방어가 §1의 프로토콜 계층에 있는 것이 옳다.
- Human FRR: 통제수집 데이터 기준 pooled 1%지만 참여자별 편차 큼(최악 27%,
  4/42명 3% 초과). 실사용자 트래픽 미측정 + lockbox 소진이라 운영 FRR은 미확정.

## 5. 정직하게 "모름"인 것 / 다음 확인

- **GPU 배포 캡차(`/srv/codex-workspaces/ms/drag-captcha`)에 §1 방어가 실제
  올라가 있는지** — `ms` 소유라 `sw`로 못 읽음(권한). `BEHAVIOR_EVENT_TRANSPORT`
  실제 값도 미확인. → `ms`/인프라 담당 확인 필요.
- 행동 AI는 GPU에 가동 중이나 `POST /predict` 0건 = 캡차가 아직 호출 안 함
  (transport off로 추정). 능력은 있고 **활성화(스위치) 문제**지 미구현이 아님.

## 7. 한 줄 결론 (정정 후)

손제작 봇은 모델이 완전 차단하고, 재생 swap 공격은 **팀이 만든 서버측 신뢰
프로토콜이 end-to-end로 차단**한다. 모델 단독의 재생 맹점(97.5%)은 레드팀으로
규명했으나 시스템 우회율이 아니다. 남은 것은 (a) 좁은 잔존(완벽 페이싱 재생),
(b) 배포 활성화 확인, (c) 실사용자 FRR 측정이다.
