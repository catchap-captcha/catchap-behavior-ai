# 발표 준비 — 지금까지 무엇을 했고 무엇이 남았나

조성원 · 2026-08-05 · M5까지 7일 · 발표까지 14일

---

## 한 장 요약

*2026-08-06 전면 갱신 — 8/05 판의 성능 숫자는 전부 틀렸다. 사유는 6절.*

**만든 것** — 캡차를 푸는 동안의 마우스 움직임으로 사람과 봇을 가르는 모델.

**지금 성능** — 현재 배포본은 처음 보는 봇에게 **74.7%** 뚫린다. 후보들은 6~11%로
내리지만, 회피율이 낮은 모델일수록 사람을 더 막는다. **맞바꿈이다.**

**승급은 못 했다** — 두 관문(회피율 ≤10% · 사람 오탐 ≤2%)을 같이 넘는 후보가
`scale_pixel` 하나인데, **그 모델은 어떻게 만들었는지 기록이 없어 재현할 수 없다.**

**이번 프로젝트의 교훈** — 방어를 만드는 것보다 **방어를 정직하게 재는 것**이 어렵다.
레드팀은 공격 표면을 100배 과소평가하고 있었고, 그걸 고친 뒤에도 **내가 그 결과를
잘못 읽어** 47%(4세대)를 74.7%(수렴값) 대신 발표 자료에 적었다.

## 1. 무엇을 만들었나

인강 플랫폼에서 자동화 프로그램이 캡차를 대신 풀고 진도를 파밍하는 것을 막는 층이다.
캡차 자체(문항 풀이·허니팟·PoW)는 민서가 만들었고, 나는 그 위에 **행동 판별**을 얹었다.

```
사용자가 캡차를 푼다
  → 200ms 단위로 포인터 이벤트를 서버에 저장 (nonce + HMAC 영수증 체인)
  → 검증 시 서버가 저장분을 다시 해싱해 대조
  → 궤적 특징 50개를 뽑아 두 모델로 채점
  → min(P_general, P_dynamics) 로 융합
```

**클라이언트가 보내는 값을 믿지 않는 구조**다. 이벤트를 서버가 보관하고, 검증 때
서버가 가진 것으로만 채점한다.

## 2. 지금 성능

후보 다섯을 같은 자로 쟀다. 회피율은 진화 레드팀 30세대(마지막 5세대 평균), 오탐은
메인 캡차 수집분에서 학습 3명(jy·p4·p5)을 한 명씩 빼고 잰 값이다.

| 모델 | 회피율 | 전체 오탐 | 최악 참여자 | 재현 | 판정 |
|---|---:|---:|---:|:---:|---|
| **배포본** | **74.7%** | 2.8% | 12.2% | ✅ | 회피 미달 |
| **scale_pixel** | **7.1%** | **1.7%** | **4.9%** | ❌ | 성적만 통과 |
| patched_weakset | 6.6% | 3.4% | 12.2% | ⛔ | 규칙 위반 |
| scale_normalized | 10.8% | 2.8% | 9.8% | ❌ | 셋 다 미달 |
| surface_aware (8/06) | 92.6% | 2.3% | 7.3% | ✅ | 회피 대폭 미달 |

```
기준  회피율 ≤10%  ·  전체 오탐 ≤2%  ·  최악 참여자 ≤5%
```

**맞바꿈이다.** 8/05 판에 "사람 오탐을 늘리지 않고 회피율만 14배 내렸다, 맞바꿈이
아니다" 라고 적은 것은 철회한다. 회피율이 낮은 모델일수록 사람을 더 막는다.

## 3. 핵심 발견 다섯 가지

### ① 레드팀이 공격 표면을 100배 과소평가하고 있었다

기존 레드팀은 모션 정책을 **무작위로 뽑아** 회피한 것을 줍는 방식이었다. 시드에 크게
흔들린다.

```
같은 모델 · 같은 예산 · 시드만 다름
  회피 28건 · 0건 · 21건 · 18건 · 1건 · 17건
```

실제 공격자는 처음부터 다시 뽑지 않는다. **먹힌 것을 남기고 그 주변을 판다.**
진화 탐색으로 바꿔 30세대를 돌렸다.

```
무작위 스윕   0.7%
진화 탐색     74.7%     ← 실제 상한 (마지막 5세대 평균)
```

**측정 도구가 약하면 방어가 강해 보인다.** 이게 이번 프로젝트에서 가장 값비싼 교훈이다.

*8/06 정정: 8/05 판에는 47% 로 적혀 있었다. 그건 4세대 값이다. 진화 탐색은 세대가
갈수록 회피율이 올라가는데(그게 이 도구의 존재 이유다) 수렴을 기다리지 않고 옮겨
적었다. 도구는 옳았고 읽는 법이 틀렸다.*

### ② 약점셋 학습은 규칙 위반이었다

7/22에 레드팀이 찾아낸 약점 2,554건을 학습에 넣어 회피율을 크게 낮췄다고 8/05에
보고했다. **그 데이터는 학습이 금지돼 있었다.**

```json
data/interim/redteam_weakness_search_iter1_20260722/*.manifest.json
{ "training_usage": "redteam_only",
  "detector_training_forbidden": true,
  "threshold_tuning_forbidden": true }
```

금지 이유는 분명하다. **그 데이터로 학습하면 그것으로 회피율을 잴 수 없게 된다.**
자를 녹여 물건을 만든 셈이다. 해당 후보(`patched_weakset_iter1_20260804`)는 성능과
무관하게 폐기한다.

다행히 약점셋 없이 학습한 `scale_pixel` 이 회피율 7.1% 를 냈다. 필요하지 않았다.

### ③ 채점 단위가 잘못돼 있었다

기존 특징은 세션 합계(`event_count`·`duration_ms`·`total_distance`)라 **드래그 횟수에
비례해 부풀었다.** 자로 그은 직선도 5번 끌면 `human_probability 1.0000` 을 받았다.
공격자에게 "여러 번 끌기"는 반복문 한 줄이다.

드래그마다 채점하고 중앙값을 쓰면 그 지렛대가 사라진다. 그리고 합계가 가리고 있던
것이 드러난다.

```
사람 드래그 2회 이상 56건
  세션 점수로는  53/56 통과
  드래그 단위로   4/56 통과
```

**다중 드래그 사람이 통과하던 것은 모델이 알아봐서가 아니라 합계가 부풀어서였다.**

### ④ 특징이 화면 크기에 딸려 있다 — 그런데 정규화는 답이 아니었다

55개 중 16개가 픽셀 단위다. 캡차 스테이지 폭이 500/640/375/333/1024로 섞여 있어
**같은 손동작이 다른 숫자로 들어간다.** 여기까지는 8/05 판 그대로다.

**정규화가 개선이라는 결론은 철회한다.** 같은 예산으로 다시 재니 반대다.

```
scale_pixel        (픽셀)     회피  7.1%
scale_normalized   (정규화)   회피 10.8%     ← 더 나쁘다
```

프로덕션도 픽셀로 계산한다. 캡차가 `x` 와 `x_normalized` 를 둘 다 보내고 특징
추출기는 그중 16개를 픽셀로 만든다. **정규화본은 프로덕션과 다른 특징 공간에 있다.**

크기 의존은 여전히 실재하는 문제이고, 해법이 정규화가 아닐 뿐이다. 8/06 수집분에
스테이지 폭이 500·375·333으로 섞여 들어와 있어 이 축을 다시 다룰 재료는 있다.

### ⑤ 장치 신호(`coalesced_count`)는 죽었다

"실제 입력 장치에서만 나오는 값"이라 기대했던 축이다. 사람 마우스 1,401건을 재보니
**평균 1.009, 2 이상이 0.9%**였다. Playwright 봇도 전부 1이다. 사전에 못박은 기준
(평균 1.3 이상)에 한참 못 미친다.

**이 축은 접는다.** 접는 것도 결과다 — 3주 남은 시점에 어디에 시간을 쓸지 정해준다.

## 4. 위협 모델 — 무엇을 막고 무엇을 못 막나

인강 사이트 자동화를 7가지로 나눠 각각 지금 방어를 대조했다.

| | 상태 |
|---|---|
| **API 직접 호출** | **차단** — PoW · Origin 검사 · 허니팟 · 레이트리밋 |
| 시험·퀴즈 자동화 | 부분 — 쿨다운·레이트리밋. 문제은행 매칭은 못 잡음 |
| 다중화(다계정·VPN) | 부분 — 기록만, 차단 안 함 |
| 재생 조작(배속·탭숨김) | **거의 없음** — 신호 자체를 안 받고 있음 |
| 매크로·오토클릭 | 미검증 — 표본 0 |
| 브라우저 자동화 | 개선안으로 대응 (3.3%) |
| 캡차 우회(AI·대행) | **못 막음** — 시각 인식은 싸고, 사람 대행은 원리적으로 불가 |

### 제일 큰 구멍은 "재생 조작"이다

배속 조작·탭 숨김 재생·자동 다음강의는 **포인터를 전혀 건드리지 않는다.** 진짜 사람이
앉아 있고 자동화는 재생 제어만 한다. 궤적 모델이 원리적으로 못 잡는다.

그런데 싸게 잡힌다. 서버가 이미 하트비트를 받고 있으므로 **`Δposition / Δwall-clock`**
비율만 보면 된다. 공격자가 못 속인다 — 하트비트를 늦추면 비율이 내려가고, 그러면
파밍이 안 된다.

**아직 담당이 정해지지 않았다.**

## 5. 정직하게 말해야 할 것

발표에서 숨기면 질문 하나로 무너진다. 미리 적어둔다.

**① 캡차 자체는 붙었고, 행동 모델은 여전히 shadow 다.** 8/06에 전용 호스트
`captcha.catchap5.com` 이 서고 위젯 계약이 확정됐다. 시청 화면·문제은행 수집 위젯은
프론트에 구현됐으나 배포 전이다. 행동 모델은 점수만 기록한다.

**② 사람 데이터는 5명 410건이 됐다.** 8/06 하루에 모았다. 다만 전부 02:36~04:39
사이라 **다른 날·다른 컨디션이 없다.**

**③ 회피율은 우리 진화 탐색 기준이다.** 더 강한 공격자를 만들면 올라갈 수 있다.
다만 지금 도구 중에서는 가장 강한 상한이고, 8/06에 그 도구를 제대로 읽는 법까지
고쳤다.

**④ 기준을 통과하는 후보는 재현할 수 없다.** `scale_pixel` 은 임시 스크립트로
만들어졌고 그 스크립트가 저장되지 않았다. 재현 가능한 후보 둘은 회피율에서 떨어진다.

**⑤ 시각 인식 봇에 대한 답이 없다.** 문항 1,796개는 레이트리밋 기준 75분이면 전량
수집 가능하고, 그 뒤로는 조회만으로 풀린다.

**⑥ 두 축을 다른 임계값에서 재고 있었다.** 회피율은 저장 임계로, 오탐은 다시 맞춘
동작점으로 쟀다. 같은 곡선 위의 두 점이 아니다. 8/06에 발견해 도구에 경고를 박았다.

## 6. 이 프로젝트에서 배운 것 — 발표의 축

**측정 도구가 방어보다 먼저다.**

3주 동안 숫자를 여러 번 뒤집었다. 전부 도구가 부실해서 생긴 일이다.

```
7/31  "FRR 0.11%"           → 메인 캡차 실측 33.3%      표면이 달랐다
8/03  "FRR 1.5%"            → 처음 보는 사람 4.5%       고른 데이터에서 쟀다
8/04  "미지 family 못 푼다"  → 풀렸다                    레드팀이 약했다
8/04  "밀봉 평가 0회"        → 이미 받았음               파일 이름만 봤다
8/06  "회피율 47% → 3.3%"    → 74.7% → 7.1%             4세대를 최종값으로 읽었다
8/06  "약점셋이 방치돼 있었다" → 학습 금지 데이터였다      매니페스트를 안 읽었다
```

**여섯 번 다 우리에게 유리한 쪽으로 틀렸다.** 검증을 안 했으면 좋은 숫자를 들고 왔을 것이다.

앞의 넷은 도구가 부실해서였다. **8/06의 둘은 도구가 옳았고 내가 잘못 읽었다.**
그래서 대책이 다르다 — 도구를 고치는 게 아니라, 수치를 옮길 때 **어느 세대·어느
조건의 값인지** 같이 적고, 데이터를 쓰기 전에 **매니페스트를 먼저 읽어야** 한다.

그래서 이번에 만든 것 중 절반이 **측정 도구**다.

```
tools/redteam_evolution_search.py    진화 레드팀 — 상한을 재는 도구
tools/lockbox_audit.py               봉인 대장 검증기
tools/per_drag_scoring.py            드래그 단위 채점 + 재현 검증
tools/frr_operating_point.py         처음 보는 사람 기준 동작점
tools/collection_split.py            수집 전 분리 규칙 고정
tools/collection_links.py            참여자 코드 생성 + 형식 검증        (8/06)
tools/build_collection_features.py   수집분 → 학습 행, 봉인 거부 내장     (8/06)
tools/frr_candidate_compare.py       후보별 참여자 단위 오탐             (8/06)
tools/train_drag_unit_candidate.py   드래그 단위 학습 + 기록             (8/06)
```

락박스 검증기는 **홀드아웃으로 표시된 3개가 사실 학습 데이터**라는 것을 찾아냈다.
그대로 채점했으면 학습 데이터로 채점하는 셈이었다.

## 7. 남은 일정

```
지금       연동 대기 (프록시 → 위젯 → verify-token)
연동 후    iframe 안 이벤트 수집 확인 · 스테이지 크기 확인
그 다음    수집 8명 × 마우스/트랙패드 · 2~3명분 봉인
그 다음    정식 재학습 → 밀봉 채점 한 번 → 승급 판정
```

**M5(8/12)까지 7일, 발표(8/19)까지 14일.**

연동이 남의 일정에 달려 있어 승급까지 갈지는 확답할 수 없다. 다만 **모델 쪽은 막힌 게
없고**, 사람만 모이면 판정이 가능한 상태다.

## 8. 발표에서 할 수 있는 말 / 못 하는 말

```
할 수 있는 말
  · 현재 배포본이 처음 보는 봇에게 74.7% 뚫린다는 것을 측정으로 밝혔다
  · 우리 레드팀이 100배 과소평가하고 있었다는 것을 찾아내고 도구를 다시 만들었다
  · 그 도구를 만든 뒤에도 내가 결과를 잘못 읽고 있었다는 것을 스스로 잡았다
  · 채점 단위(드래그) 결함을 측정으로 찾아 고쳤다
  · 하루에 사람 5명 410건을 모으고, 결과를 보기 전에 봉인을 갈랐다
  · 무엇을 못 막는지 정확히 안다 (시각 인식 봇 · 사람 대행 · 재생 조작)

못 하는 말
  · "실서비스에서 봇을 막고 있다"        → 아직 shadow, 수집 위젯 배포 전
  · "회피율을 47% → 3.3% 로 낮췄다"      → 철회. 74.7% → 최선 후보 7.1%
  · "사람 오탐을 안 늘리고 회피율만 낮췄다" → 철회. 맞바꿈이다
  · "정규화가 개선의 핵심이었다"          → 철회. 정규화본이 더 나쁘다
  · "승급했다"                          → 기준을 넘는 후보가 재현 불가
```

8/05 판은 **"성능이 부족해서 못 올린 게 아니라, 올려도 된다고 말할 근거가 부족해서
안 올렸다"** 였다. **8/06 기준으로는 반대다.**

```
근거는 생겼다      사람 5명 410건 · 봉인 사전 고정 · 같은 자로 잰 후보 비교표
성능이 모자란다    기준을 넘는 후보가 하나인데, 그 모델은 재현할 수 없다
```

**"측정을 고치니 방어가 생각보다 훨씬 약했다"** 가 정확한 서술이다. 이게 나쁜
발표 내용이 아니다 — 3주 동안 다섯 번 숫자가 뒤집혔고 **다섯 번 다 우리에게 유리한
쪽으로 틀렸다.** 그걸 전부 스스로 잡아낸 과정이 이 프로젝트의 결과물이다.
