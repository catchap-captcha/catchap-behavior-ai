# 발표 준비 — 지금까지 무엇을 했고 무엇이 남았나

조성원 · 2026-08-05 · M5까지 7일 · 발표까지 14일

---

## 한 장 요약

**만든 것** — 캡차를 푸는 동안의 마우스 움직임으로 사람과 봇을 가르는 모델.

**지금 성능** — 처음 보는 봇의 회피율을 47%에서 3.3%로 내렸다. 사람 오탐은 오히려
줄었다. 승급 기준(≤10%)을 통과한다.

**승급은 못 했다** — 성능이 부족해서가 아니라 **증명할 데이터가 없어서**다.
검증용 사람 데이터가 2명뿐이고, 봉인 시험지가 다 떨어졌다.

**이번 프로젝트의 교훈** — 방어를 만드는 것보다 **방어를 정직하게 재는 것**이 어렵다.
우리 레드팀은 공격 표면을 60배 과소평가하고 있었고, 그걸 8/04에야 발견했다.

---

## 1. 무엇을 만들었나

인강 플랫폼에서 자동화 프로그램이 캡차를 대신 풀고 진도를 파밍하는 것을 막는 층이다.
캡차 자체(문항 풀이·허니팟·PoW)는 민서가 만들었고, 나는 그 위에 **행동 판별**을 얹었다.

```
사용자가 캡차를 푼다
  → 200ms 단위로 포인터 이벤트를 서버에 저장 (nonce + HMAC 영수증 체인)
  → 검증 시 서버가 저장분을 다시 해싱해 대조
  → 궤적 특징 50개를 뽑아 두 모델로 채점
  → min(P_general, P_dynamics) 로 융합
```

**클라이언트가 보내는 값을 믿지 않는 구조**다. 이벤트를 서버가 보관하고, 검증 때
서버가 가진 것으로만 채점한다.

## 2. 지금 성능

| 항목 | 기준 | 현재 배포본 | 개선안 (미배포) |
|---|---|---:|---:|
| **미지 family 최악 ASR** | ≤10% | **47%** ❌ | **3.3%** ✅ |
| 알려진 Bot ASR | ≤5% | 3.6% ✅ | ✅ |
| 처음 보는 사람 오탐 (레거시 17명) | ≤3% | 0.7~2.2% ✅ | 1.17% ✅ |
| 처음 보는 사람 오탐 (메인 캡차 1명) | ≤3% | 4.5% ❌ | 미측정 |
| 새 외부 holdout | 필요 | **없음** ❌ | ❌ |
| 메인 캡차 사람 5명 | 5명 | **2명** ❌ | ❌ |

**개선안은 사람 오탐을 늘리지 않고 회피율만 14배 내렸다.** 맞바꿈이 아니다.

## 3. 핵심 발견 다섯 가지

### ① 레드팀이 공격 표면을 60배 과소평가하고 있었다

기존 레드팀은 모션 정책을 **무작위로 뽑아** 회피한 것을 줍는 방식이었다. 시드에 크게
흔들린다.

```
같은 모델 · 같은 예산 · 시드만 다름
  회피 28건 · 0건 · 21건 · 18건 · 1건 · 17건
```

실제 공격자는 처음부터 다시 뽑지 않는다. **먹힌 것을 남기고 그 주변을 판다.**
진화 탐색으로 바꿔 30세대를 돌리니 수렴했다.

```
무작위 스윕   0.7%
진화 탐색     47%       ← 실제 상한
```

**측정 도구가 약하면 방어가 강해 보인다.** 이게 이번 프로젝트에서 가장 값비싼 교훈이다.

### ② 그리고 막을 수 있었다 — 안 해봤을 뿐

7/22에 레드팀이 찾아낸 약점 2,554건이 **학습에 안 들어간 채 방치**돼 있었다.
넣고 재학습하니 같은 사람 오탐률에서:

```
진화 탐색 회피    47% → 5.8%
다른 탐색 약점셋   70% → 0.0%
외부 holdout      13% → 0.0%
처음 보는 사람    1.62% → 1.17%   (좋아짐)
```

7/22에 다른 종류의 하드 네거티브가 실패했고(사람 오탐 9.06%), 나는 **"약점 학습은
안 된다"는 결론을 재검증 없이 받아 적었다.** 그게 이 항목을 8/04까지 막고 있었다.

### ③ 채점 단위가 잘못돼 있었다

기존 특징은 세션 합계(`event_count`·`duration_ms`·`total_distance`)라 **드래그 횟수에
비례해 부풀었다.** 자로 그은 직선도 5번 끌면 `human_probability 1.0000` 을 받았다.
공격자에게 "여러 번 끌기"는 반복문 한 줄이다.

드래그마다 채점하고 중앙값을 쓰면 그 지렛대가 사라진다. 그리고 합계가 가리고 있던
것이 드러난다.

```
사람 드래그 2회 이상 56건
  세션 점수로는  53/56 통과
  드래그 단위로   4/56 통과
```

**다중 드래그 사람이 통과하던 것은 모델이 알아봐서가 아니라 합계가 부풀어서였다.**

### ④ 특징이 화면 크기에 딸려 있었다

50개 중 17개가 픽셀 단위였다. 캡차 스테이지 폭이 500/640/375/333/1024로 섞여 있어,
**같은 손동작이 다른 숫자로 들어가고 있었다.** 정규화 좌표로 바꾸니 회피율이
6.3% → 3.3%로 오히려 좋아졌다. 절대 스케일은 신호가 아니라 잡음이었다.

### ⑤ 장치 신호(`coalesced_count`)는 죽었다

"실제 입력 장치에서만 나오는 값"이라 기대했던 축이다. 사람 마우스 1,401건을 재보니
**평균 1.009, 2 이상이 0.9%**였다. Playwright 봇도 전부 1이다. 사전에 못박은 기준
(평균 1.3 이상)에 한참 못 미친다.

**이 축은 접는다.** 접는 것도 결과다 — 3주 남은 시점에 어디에 시간을 쓸지 정해준다.

## 4. 위협 모델 — 무엇을 막고 무엇을 못 막나

인강 사이트 자동화를 7가지로 나눠 각각 지금 방어를 대조했다.

| | 상태 |
|---|---|
| **API 직접 호출** | **차단** — PoW · Origin 검사 · 허니팟 · 레이트리밋 |
| 시험·퀴즈 자동화 | 부분 — 쿨다운·레이트리밋. 문제은행 매칭은 못 잡음 |
| 다중화(다계정·VPN) | 부분 — 기록만, 차단 안 함 |
| 재생 조작(배속·탭숨김) | **거의 없음** — 신호 자체를 안 받고 있음 |
| 매크로·오토클릭 | 미검증 — 표본 0 |
| 브라우저 자동화 | 개선안으로 대응 (3.3%) |
| 캡차 우회(AI·대행) | **못 막음** — 시각 인식은 싸고, 사람 대행은 원리적으로 불가 |

### 제일 큰 구멍은 "재생 조작"이다

배속 조작·탭 숨김 재생·자동 다음강의는 **포인터를 전혀 건드리지 않는다.** 진짜 사람이
앉아 있고 자동화는 재생 제어만 한다. 궤적 모델이 원리적으로 못 잡는다.

그런데 싸게 잡힌다. 서버가 이미 하트비트를 받고 있으므로 **`Δposition / Δwall-clock`**
비율만 보면 된다. 공격자가 못 속인다 — 하트비트를 늦추면 비율이 내려가고, 그러면
파밍이 안 된다.

**아직 담당이 정해지지 않았다.**

## 5. 정직하게 말해야 할 것

발표에서 숨기면 질문 하나로 무너진다. 미리 적어둔다.

**① 실서비스에 아직 안 붙어 있다.** 캡차는 독립 구동 중이고, 플랫폼 `/captcha` 는
"API 캡챠 위젯 자리" 자리표시자 상태다. 행동 모델은 `shadow` 로 점수만 기록한다.

**② 사람 데이터가 2명이다.** FRR 4.5%는 참여자 1명에게서 잰 값이다.

**③ 3.3%는 우리 진화 탐색 기준이다.** 더 강한 공격자를 만들면 올라갈 수 있다.
다만 지금 도구 중에서는 가장 강한 상한이다.

**④ 개선안은 정식 파이프라인으로 재현하지 않았다.** 임시 학습 모델의 숫자다.

**⑤ 시각 인식 봇에 대한 답이 없다.** 문항 1,796개는 레이트리밋 기준 75분이면 전량
수집 가능하고, 그 뒤로는 조회만으로 풀린다.

## 6. 이 프로젝트에서 배운 것 — 발표의 축

**측정 도구가 방어보다 먼저다.**

3주 동안 숫자를 여러 번 뒤집었다. 전부 도구가 부실해서 생긴 일이다.

```
7/31  "FRR 0.11%"           → 메인 캡차 실측 33.3%      표면이 달랐다
8/03  "FRR 1.5%"            → 처음 보는 사람 4.5%       고른 데이터에서 쟀다
8/04  "미지 family 못 푼다"  → 3.3%                     레드팀이 약했다
8/04  "밀봉 평가 0회"        → 이미 받았음               파일 이름만 봤다
```

**네 번 다 우리에게 유리한 쪽으로 틀렸다.** 검증을 안 했으면 좋은 숫자를 들고 왔을 것이다.

그래서 이번에 만든 것 중 절반이 **측정 도구**다.

```
tools/redteam_evolution_search.py   진화 레드팀 — 상한을 재는 도구
tools/lockbox_audit.py              봉인 대장 검증기
tools/per_drag_scoring.py           드래그 단위 채점 + 재현 검증
tools/frr_operating_point.py        처음 보는 사람 기준 동작점
tools/collection_split.py           수집 전 분리 규칙 고정
```

락박스 검증기는 **홀드아웃으로 표시된 3개가 사실 학습 데이터**라는 것을 찾아냈다.
그대로 채점했으면 학습 데이터로 채점하는 셈이었다.

## 7. 남은 일정

```
지금       연동 대기 (프록시 → 위젯 → verify-token)
연동 후    iframe 안 이벤트 수집 확인 · 스테이지 크기 확인
그 다음    수집 8명 × 마우스/트랙패드 · 2~3명분 봉인
그 다음    정식 재학습 → 밀봉 채점 한 번 → 승급 판정
```

**M5(8/12)까지 7일, 발표(8/19)까지 14일.**

연동이 남의 일정에 달려 있어 승급까지 갈지는 확답할 수 없다. 다만 **모델 쪽은 막힌 게
없고**, 사람만 모이면 판정이 가능한 상태다.

## 8. 발표에서 할 수 있는 말 / 못 하는 말

```
할 수 있는 말
  · 처음 보는 봇의 회피율을 47% → 3.3% 로 낮췄다 (사람 오탐 증가 없이)
  · 우리 레드팀이 60배 과소평가하고 있었다는 것을 찾아내고 도구를 다시 만들었다
  · 채점 단위·특징 스케일의 구조적 결함 두 개를 측정으로 찾아 고쳤다
  · 무엇을 못 막는지 정확히 안다 (시각 인식 봇 · 사람 대행 · 재생 조작)

못 하는 말
  · "실서비스에서 봇을 막고 있다"        → 아직 shadow, 위젯 미연결
  · "사람 오탐률이 X% 다"                → 참여자 2명
  · "승급했다"                          → 검증 데이터 부족
```

**"성능이 부족해서 못 올린 게 아니라, 올려도 된다고 말할 근거가 부족해서 안 올렸다"**
가 정확한 서술이다.
