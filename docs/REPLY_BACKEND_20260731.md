## 1. 무엇을 쟀나

실제 Chromium을 띄워 메인 캡차를 푸는 봇을 만들어 돌렸습니다
(`ai-service/tools/playwright_solve_captcha.mjs`).

지금까지 제 레드팀 도구는 HTTP로 이벤트를 직접 만들어 쐈습니다. 그래서 브라우저가
찍는 값이 전부 null이었고, "브라우저를 안 썼다"는 것만 잡혔습니다. 실제 공격자는
브라우저를 씁니다. 그 격차를 메우려고 만든 도구입니다.

```
                  is_trusted   pointer_type   pressure
사람 브라우저        true         mouse         (값 있음)
Playwright 봇       true         mouse          0.5
HTTP 스크립트 봇     null         null           null
```

**새로 넣은 장치 신호로는 브라우저 봇과 사람이 구분되지 않습니다.** 예상은 했지만
이제 측정값입니다.

행동 모델 점수도 마찬가지입니다. 자로 그은 직선 궤적으로 객체를 여러 번 끈 봇이
`human_probability 1.0` → **allow** 를 받았습니다.

## 2. 그래서 승급 설계에 뭘 반영해야 하나

### ① 캡차 승급은 "사람인지 확인"이 아니라 "비용 부과"로 보셔야 합니다

승급의 실질 효과는 세 가지입니다.

```
허니팟          JSON을 긁는 봇만 잡습니다. 이미지를 보고 고르는 봇은 자연스럽게 피합니다
PoW            비용. 정상 동작 확인했습니다(아래 3절)
문제를 푸는 능력  시각 인식이 필요합니다. 지금 가장 실질적인 장벽입니다
```

행동 모델은 아직 `shadow`이고, 오늘 결과로는 `active`로 올릴 수 없습니다.
**승급을 붙이실 때 "캡차를 통과했으니 사람"이라는 전제는 두지 마세요.**
통과는 "봇이라면 최소한 브라우저와 시각 인식을 갖췄다" 정도입니다.

### ② 그래도 승급은 의미가 있습니다 — 다만 값이 달라집니다

대량 자동화의 단가를 올리는 효과는 확실합니다. 브라우저를 띄우는 봇은 HTTP 스크립트보다
수십 배 비쌉니다. **소수 정예 공격은 못 막고, 대량 파밍은 막습니다.**

의심 점수 임계를 정하실 때 이 구분이 들어가면 좋겠습니다. "캡차로 걸러진다"가 아니라
"캡차로 단가가 오른다"가 맞는 서술입니다.

## 3. 제가 오늘 틀린 것 하나 (기록용)

배포된 캡차 번들에서 PoW 워커가 `ReferenceError`를 던지는 걸 보고 **"PoW가 우회되고
있다"**고 민서님께 보고했습니다. **틀렸습니다.**

`onerror` 분기가 메인스레드 폴백으로 진짜 솔버를 돌리고 있었습니다. 저는 앞쪽
가드절의 `t(null)`을 보고 `onerror`도 그럴 거라 단정했고, 정작 그 분기를 안 읽었습니다.
민서님이 `--nopow`로 서버를 실측해 `pow_failed`를 확인해 주셨습니다.

**PoW는 정상 작동 중입니다.** 위 2절 ①에 그렇게 반영했습니다.

## 4. 부탁드릴 것 2개

### ① `SUSPICION_SESSION_CONFLICT` 5 → 2 (감사 9번)

7/30에 드린 건인데 진행 상태를 모르겠습니다. 노트북→폰→노트북 한 번이면 임계 10에
닿는 값이라, 시나리오를 돌리기 전에 정해두는 게 맞다고 봅니다. 시나리오 계획이
그대로 살아 있다면 이것만 먼저 반영하시면 됩니다.

### ② `solve_time_ms` 서버 계산 — 오늘 결과로 우선순위가 올라갑니다

7/30에 "문항당 3초 제한보다 이쪽이 진짜 가치"라고 썼는데, 오늘 결과가 그걸 강화합니다.

행동 모델이 궤적만으로는 브라우저 봇을 못 가른다는 게 확인됐습니다. 남는 건
**공격자가 조작할 수 없는 값**인데, 서버가 재는 시간이 정확히 그런 값입니다.
클라이언트가 보내는 지금 값으로는 아무것도 못 합니다.

DDL 없이 되는 작업이라면 다음 주 안에 들어갈 수 있을지 봐주시면 좋겠습니다.
