# 레드팀 기준선 재측정 — 발표 숫자가 틀렸다

조성원 · 2026-08-06

---

## 결론

**8/04에 보고한 회피율이 틀렸고, 어느 모델이 최선인지도 틀렸습니다.**

같은 예산(30세대 · 40개체 · 정책당 12건 · seed 20260804)으로 후보 넷을 각자의
좌표계에서 다시 쟀습니다.

| 모델 | 좌표계 | 회피율 (마지막 5세대) | 사람 통과율¹ |
|---|---|---:|---:|
| **revalidation (배포본)** | 픽셀 | **74.7%** | 100.0% |
| scale_pixel | 픽셀 | **7.1%** | 96.7% |
| patched_weakset | 픽셀 | **6.6%** | 81.7% |
| scale_normalized | 정규화 | **10.8%** | 95.0% |

¹ 레거시 120건 · 참여자별 보정 미적용 — **잠정치**. 5절 참조.

```
8/04 보고    배포본 47%  →  정규화 개선안 3.3%   "정규화가 핵심, 기준 통과"
실측         배포본 74.7% → 정규화 개선안 10.8%  "정규화는 오히려 제일 나쁘다"
```

**세 가지가 뒤집혔습니다.**

1. 배포본은 47% 가 아니라 **74.7%** — 훨씬 약합니다
2. 정규화 개선안은 3.3% 가 아니라 **10.8%** — 승급 기준 ≤10% 미달
3. **정규화가 개선의 핵심이 아니었습니다** — 픽셀 모델 둘(7.1% · 6.6%)이 더 낫습니다

---

## 1. 왜 다시 쟀나

원래 걱정은 다른 것이었습니다. 프로덕션이 정규화 좌표를 쓰는데 제 레드팀은 픽셀을
던지는 것 아닌가 — 즉 **두 숫자를 다른 자로 잰 것 아닌가** 였습니다.

**그 걱정은 틀렸습니다.** 확인 결과 방법론은 성립합니다.

### 좌표계 실측

특징 55개 중 **16개가 픽셀 기반**입니다. 같은 궤적을 두 방식으로 넣어 비교했습니다.

```
total_distance       픽셀  2502.37    정규화  3.42
avg_speed            픽셀     0.0930  정규화  0.000127
direction_changes    픽셀    30       정규화  0
pause_count          픽셀    27       정규화  293
```

프로덕션은 캡차가 `x`·`x_normalized` 를 둘 다 보내므로 이 16개는 **픽셀로 계산**됩니다.
제 레드팀도 플래그 없이 돌리면 픽셀입니다. **조건이 같습니다.**

### 각 모델의 학습 좌표계

메타데이터가 없어서 사람 궤적 120건을 두 방식으로 넣어 역추정했습니다.

| 모델 | 픽셀 입력 | 정규화 입력 | 판정 |
|---|---:|---:|---|
| revalidation (배포본) | 100.0% | 56.7% | 픽셀 |
| scale_pixel | 96.7% | 83.3% | 픽셀 |
| **scale_normalized** | **2.5%** | **95.0%** | **정규화** |
| patched_weakset | 81.7% | 72.5% | 픽셀 |

`scale_normalized` 는 2.5% vs 95.0% 로 명확합니다. 각 모델을 **자기 좌표계로** 재면
비교가 성립합니다.

그런데 저는 **초반 세대 값을 최종값으로 적었습니다.** 배포본은 4세대에서 47.5%,
개선안은 4세대에서 1.9% 였고, 제 문서의 47% · 3.3% 가 거기서 왔습니다.

**도구는 옳았는데 읽는 법이 틀렸습니다.**

## 3. 정규화가 핵심이라는 서술이 틀렸다

8/04에 저는 "크기 정규화로 6.3% → 3.3%" 라고 적고, 정규화를 개선의 핵심으로
서술했습니다. **반대입니다.**

```
scale_pixel        (픽셀)     7.1%
patched_weakset    (픽셀)     6.6%    ← 회피율 최저
scale_normalized   (정규화)  10.8%    ← 셋 중 최악
```

**픽셀 모델 둘이 정규화 모델보다 낫습니다.** 정규화는 프로덕션 좌표계와도 다르고
(프로덕션은 16개 특징을 픽셀로 계산), 회피율도 더 나쁩니다.

`STATUS_FOR_PRESENTATION_20260805.md` 의 "④ 특징이 화면 크기에 딸려 있었다 —
정규화하니 6.3% → 3.3% 로 오히려 좋아졌다" 항목은 철회해야 합니다.

## 4. 승급 판정 — 어느 후보도 두 관문을 같이 통과하지 못한다

```
관문   회피율 ≤ 10%        (처음 보는 봇 계열 최악)
관문   사람 오탐 ≤ 3%      (실험 후보) · ≤ 1% (Production)
```

| 모델 | 회피율 | 사람 오탐¹ | 판정 |
|---|---:|---:|---|
| revalidation (배포본) | 74.7% ❌ | 0.0% ✅ | 회피 미달 |
| **scale_pixel** | **7.1% ✅** | **3.3% △** | **가장 근접** |
| patched_weakset | 6.6% ✅ | 18.3% ❌ | 오탐 미달 |
| scale_normalized | 10.8% ❌ | 5.0% ❌ | 둘 다 미달 |

**scale_pixel 이 가장 균형 잡혀 있습니다.** 8/04 보고에서 제가 주목하지 않았던
모델입니다.

다만 사람 오탐 수치는 잠정치입니다(5절). **오탐을 제대로 다시 재기 전에는
어느 것도 후보로 확정할 수 없습니다.**

## 5. 개선 방향 자체는 살아 있다

```
배포본            74.7%
최선 후보          6.6~7.1%
                  약 10배
```

숫자가 바뀌었을 뿐 **방향은 같습니다.** 그리고 배포본이 74.7% 라는 것은
**현재 프로덕션 방어가 생각보다 훨씬 약하다**는 뜻이라, 개선을 서둘러야 할 이유가
오히려 커졌습니다.

## 6. 사람 오탐도 제대로 다시 쟀다

`tools/frr_candidate_compare.py` 를 새로 만들어 메인 캡차 수집분(실질 2명)으로
쟀습니다. **봉인 홀드아웃은 열지 않았습니다** — `lockbox_audit` 이 h2219 를
배포본에 소진된 것으로 표시하고 있고, 정식 재학습 계획이 있으면 열지 않는 게
규칙 1번입니다.

### 측정이 맞다는 근거

```
배포본 · 세션 단위 FRR   34.1%
7/31 메인 캡차 실측       33.3%
```

**알려진 값을 재현합니다.** 파이프라인이 옳습니다.

### 그전 시도가 왜 60% 가 나왔나

드래그 중앙값에 **세션 임계값(0.99995)** 을 그대로 들이댔습니다. 드래그 점수는
세션 점수보다 훨씬 낮게 깔려서, 사람의 60% 가 잘려나갔습니다.

```
세션 단위 임계    0.99995      전체 세션 특징용
드래그 단위 임계   별도 보정 필요  (app/config.py per_drag_threshold = 0.01)
```

**두 단위는 임계값을 공유할 수 없습니다.**

### 결과 — 한 사람에서 맞추고 다른 사람에서 재기

| 모델 | 세션 단위 | sw→데모 | 데모→sw |
|---|---:|---:|---:|
| revalidation (배포본) | 34.1% | 0.0% | 3.0% |
| scale_pixel | 47.5% | 7.9% | 0.5% |
| patched_weakset | 80.5% | 6.3% | 0.0% |
| scale_normalized | 42.5% | 4.8% | 0.0% |

**드래그 단위가 세션 단위를 압도합니다.** 8/03 결론이 재확인됐습니다.

## 8. 그런데 이 숫자들 자체를 못 믿는다 — 사람이 둘뿐이다

같은 모델이 **어느 사람에서 맞추느냐에 따라 0.0% 와 7.9% 를 오갑니다.**

```
scale_pixel   sw 에서 맞추고 데모에서 재면   7.9%
              데모에서 맞추고 sw 에서 재면   0.5%
```

**16배 차이입니다.** 이게 "참여자 2명"의 실제 의미입니다. 어느 쪽을 골라 보고하든
그건 측정이 아니라 선택입니다.

그리고 맞춰진 동작점 상당수가 0.0000 근처로 나옵니다 — 사람 세션의 2% 분위가
사실상 0 이라, 그 지점의 "0.0%" 는 의미가 약합니다.

**승급 판정이 데이터 부족으로 막혀 있다는 것을 이 표가 정량적으로 보여줍니다.**
성능이 부족해서가 아니라, 같은 모델을 두 번 재면 16배가 벌어지기 때문입니다.

## 7. 이번 건의 교훈

이 프로젝트에서 숫자가 뒤집힌 게 이번이 다섯 번째입니다.

```
7/31  "FRR 0.11%"            → 실측 33.3%          표면이 달랐다
8/03  "FRR 1.5%"             → 처음 보는 사람 4.5%  고른 데이터에서 쟀다
8/04  "미지 family 못 푼다"   → 3.3%                레드팀이 약했다
8/04  "밀봉 평가 0회"         → 이미 받았음          파일 이름만 봤다
8/06  "회피율 47% → 3.3%"     → 74.7% → 10.8%       초반 세대를 최종값으로 읽었다
```

**다섯 번 다 우리에게 유리한 쪽으로 틀렸습니다.**

앞의 네 번은 도구가 부실해서였습니다. **이번은 도구는 옳았고 제가 잘못 읽었습니다.**
그래서 대책이 다릅니다 — 도구를 고치는 게 아니라, **수치를 문서에 옮길 때 어느
세대·어느 조건의 값인지 같이 적어야 합니다.**
