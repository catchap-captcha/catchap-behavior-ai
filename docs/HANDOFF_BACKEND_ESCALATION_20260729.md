# 김태형님께 — 이상행동 감지 시 캡차 승급 제안 (2026-07-29)

보낸 사람: 최성우 (행동 기반 봇 판별 AI)

---

## 0. 하고 싶은 것

```
평소 인강 시청 — 캡차 없음
      ↓  이상행동 감지
메인 캡차(김민서 드래그) 띄움
      ↓  사용자가 푼다
푸는 동안 궤적 수집 → AI 가 봇인지 판별
      ↓
통과 → 시청 계속 / 의심 → 재출제
```

**기존 인강 체크포인트 캡차는 건드리지 않습니다.** 그건 "이 대목 봤는가"를 묻는 학습 확인이고,
이건 "봇 아닌가"를 묻는 별개 장치입니다. 뜨는 이유가 다릅니다.

## 1. 왜 이 방식인가

지금까지 AI를 실제 판정에 못 쓴 이유는 오탐률을 측정하지 못했기 때문입니다. 실사용 트래픽이
하루 2~4건이라 앞으로도 당분간 못 잡습니다.

그런데 승급 방식은 오탐의 대가가 다릅니다:

```
기존:  캡차 통과 → AI 가 봇 판정 → 차단          오탐 = 정상 사용자 차단
승급:  이상행동 → 캡차 표시 → 풀면 통과          오탐 = 캡차 한 번 더 품
```

오탐 비용이 "차단"에서 "캡차 1회"로 내려갑니다. **오탐률을 정밀 측정하지 않아도 쓸 수 있는
유일한 구조**입니다.

그리고 인강 보안 관점에서, 진도 위조는 이미 서버측 속도 상한이 막고 있으므로 자동화의 남은
이득은 **"사람이 앉아 있지 않아도 된다"** 뿐입니다. 승급 캡차가 정확히 그걸 겨냥합니다.

## 2. 준비된 것 / 만들 것

| | 상태 |
|---|---|
| 캡차 임베드 위젯 (`widget.js`, `?embed=1&lecture=`) | ✅ 김민서님이 만드셨습니다 |
| 토큰 서버검증 (`POST /api/verify-token`, 강의ID 일치, 1회용) | ✅ 있습니다 |
| 캡차 안 궤적 수집 + AI 판별 | ✅ `origin/sw-captcha` 병합 완료, 배포 대기 |
| 행동 AI | ✅ GPU 서버 `127.0.0.1:8010` 가동, DB 연결, 재생 탐지 동작 |
| **이상행동 누적 + 승급 트리거** | ❌ **이것만 없습니다 — 백엔드 작업** |

## 3. 감지 신호 — 이미 계산하고 있는데 버려집니다

새로 탐지 로직을 만들 필요가 없습니다. `lecture_service.py`가 하트비트마다 이미 계산합니다.

| 신호 | 지금 | 제안 |
|---|---|---|
| **position 전진 속도 위반** — `SPEED_FACTOR=2.5` + `HEARTBEAT_HEADROOM_SEC=5` 초과 | 클램프하고 버림 | 위반 횟수 누적 |
| **동시접속 충돌** — `claim_session`이 `SESSION_TTL_SEC` 내 재접속에 409 | 예외 던지고 끝 | 누적 |
| **체크포인트 연속 오답** — `MAX_CHECKPOINT_FAILS=3` 도달 | `REWIND_SEC` 되감기 | 누적 |

세 신호 모두 **"실제로 앉아서 보고 있지 않다"**를 가리킵니다.

### 누적할 자리 — `suspicion` 컬럼이 이미 있습니다

`lecture_watch_progress.suspicion` (마이그레이션 `lecture_beh_01_watch_sessions.py`).

다만 **2026-07-17에 의도적으로 걷어내셨다**는 걸 알고 있습니다:

```
# ---- 랜덤 간격·의심 가중: 제거됨(0717) ----
# ... 거기 딸려 있던 suspicion(의심 누적 시 간격 축소)과
# tab_hidden 자기신고도 좁힐 간격이 사라져 함께 걷어냈다.
```

**되살리자는 게 아니라 용도가 다릅니다.** 예전엔 "체크포인트 간격을 좁히는" 감시 목적이었고,
지금은 "봇 판별 캡차를 띄우는" 트리거입니다. 체크포인트 간격은 고정 핀 그대로 두고,
별개 캡차를 띄우는 데만 씁니다.

> **정정(2026-07-29)**: 위에서 "컬럼이 남아 있어 되살리기 쉽다"고 썼는데 **틀렸습니다.**
> 프로덕션 `lecture_watch_progress`를 확인한 결과 `suspicion` 컬럼은 `lecture_pin_02`에서
> **실제로 DROP됐습니다.** 남아 있는 건 `exempt_streak`(미사용)과 `checkpoint_fails`(사용중)뿐입니다.
> 따라서 새 컬럼 추가(마이그레이션)가 필요하고, `bot_suspicion` 이라는 이름으로 준비했습니다.
> 구현·패치는 `integration/backend-escalation/` 를 보세요.

## 4. 구현 (백엔드)

### 4-1. 누적

하트비트 처리에서 신호 발생 시 가산. 초안:

| 신호 | 가중 |
|---|---|
| position 속도 위반 | +3 |
| 동시접속 충돌 | +5 |
| 체크포인트 3연속 오답 | +4 |
| 정상 하트비트 N회 연속 | -1 (감쇠) |

감쇠가 없으면 장시간 시청에서 누적만 되어 결국 전원이 캡차를 봅니다. 필요합니다.

### 4-2. 임계 초과 → 캡차 요구

```
suspicion >= THRESHOLD  →  진도 응답에 { captcha_required: true, lecture_id: ... }
```

초기값은 **보수적으로** 잡는 걸 권합니다(예: 10 — 속도 위반 4회쯤). 관측 후 조정하면 됩니다.

### 4-3. 프론트

`captcha_required`를 받으면 김민서님 위젯을 붙입니다.

```html
<div id="catchap"></div>
<script>
  window.catchapOnVerified = function (token, lectureId) {
    // 백엔드로 token 전송
  };
</script>
<script src="https://<캡차호스트>/widget.js"
        data-target="#catchap" data-lecture-id="LEC-2026-01"></script>
```

캡차를 푸는 동안 시청은 멈추는 게 자연스럽습니다.

### 4-3b. ⚠️ 마이그레이션은 백엔드 계정으로 실행할 수 없습니다 (2026-07-29 정정)

프로덕션 DB 권한을 확인한 결과, 백엔드 런타임 계정은 **DML 전용**입니다.

```
GRANT USAGE ON *.*
GRANT SELECT, INSERT, UPDATE, DELETE ON catchap_dev_db.*
        ↑ ALTER / CREATE / DROP 없음
```

따라서 `alembic upgrade head` 를 백엔드 계정으로 돌리면 `ALTER command denied` 로 실패합니다.
기존 69개 마이그레이션은 **DDL 권한을 가진 별도 계정**으로 적용된 것으로 보입니다
(앱이 실수로 스키마를 바꾸지 못하게 분리한 설계로, 그 자체는 옳습니다).

**즉 컬럼 추가는 DB 담당자 작업입니다.** 실행 방식에 따라 둘로 갈립니다.

**(a) DDL 계정으로 `alembic upgrade head`** — 권장. 사슬이 정상적으로 진행됩니다.
다만 프로덕션이 `course_order_01` 이라 **`course_payment_pg_02`(결제) 가 함께 적용됩니다.**
골라 적용할 수 없습니다. 결제 마이그레이션을 일부러 보류한 상태라면 먼저 조율이 필요합니다.

**(b) SQL 수동 적용** — 아래 한 줄입니다.

```sql
ALTER TABLE lecture_watch_progress
  ADD COLUMN bot_suspicion INT NOT NULL DEFAULT 0;
```

⚠️ **이 경우 `alembic_version` 을 건드리지 마세요.** `lecture_botsusp_01` 로 stamp 하면
alembic 은 그 앞의 `course_payment_pg_02`(결제)까지 적용된 것으로 간주합니다 —
실제로는 적용되지 않았으므로 **결제 마이그레이션이 영구히 누락됩니다.**
버전을 그대로 두면 나중에 (a)로 정상 적용할 때 컬럼 존재 검사가 있어 중복 없이 넘어갑니다
(마이그레이션 파일에 `if _COL in cols: return` 을 넣어뒀습니다).

### 4-4. 토큰 검증 → 카운터 리셋

```
백엔드 → POST <캡차호스트>/api/verify-token
         헤더: X-Captcha-Site-Secret
         본문: { token, purpose:"lecture", session_id, lecture_id }
       → { success: true, lecture_id, challenge_id }
```

**성공하면** `suspicion = 0`으로 리셋하고 시청 계속.
**실패/토큰 없음이면** 진도 진행을 막습니다. 여기는 fail-closed가 맞습니다 —
캡차를 통과하지 못했으면 계속 볼 이유가 없습니다.

브라우저가 "통과했다"고 말하는 걸 믿지 않고 **서버가 캡차 서버에 직접 확인**하는 구조입니다.
클라이언트가 토큰을 위조할 수 없습니다.

## 5. 단계적 적용

```
1단계  승급은 규칙 신호로만 판단. AI 는 캡차 안에서 shadow 로 관측만
2단계  승급 트래픽이 표본이 됨 → 오탐률 측정
3단계  AI 점수를 승급 판정에 반영
4단계  AI step_up 을 캡차 재출제에 반영
```

**1단계만으로도 지금보다 낫습니다.** 이상행동에 캡차가 뜨고, 그 캡차는 궤적 위조를 막습니다.

## 6. 되돌리기

- `THRESHOLD`를 크게(또는 무한) → 승급 발생 안 함
- 캡차 쪽 `BEHAVIOR_EVENT_TRANSPORT=off` → 궤적 수집·AI 호출 중단

둘 다 코드 롤백 없이 설정만으로 됩니다.

## 7. 확인 부탁드릴 것

1. `suspicion` 컬럼 재사용 vs 신규 컬럼 — 어느 쪽이 좋으신지
2. 가중치·임계값 초기값 (제 초안은 근거 없는 출발점입니다)
3. 승급을 어디까지 걸지 — 시청 중 / 강의 완료 직전 / 이수증 발급 전
4. 캡차 푸는 동안 영상을 멈출지

제가 할 수 있는 부분(캡차·AI)은 준비돼 있습니다. 백엔드 쪽 구현은 필요하시면 제가 초안을
올리고 태형님 리뷰를 받는 방식도 괜찮습니다.

## 참고 — 별건 발견 사항

인강 방어를 살펴보다 확인한 것으로, 이 제안과 별개입니다.

**`course_exam_*`에 자동화 방어가 없습니다.** 시간 제한·제출 속도 하한·응시 레이트리밋·캡차가
전부 없고, mastery 설계(맞힌 문항은 영구 정복, 틀린 것만 재출제)가 시도 비용 0과 결합되어
**무작위 제출 반복으로 수료가 가능**합니다. 문항 50개 기준 약 15라운드, 자동화로 수십 초입니다.

다행히 `course_exam_*`이 아직 0행이라 서비스 전입니다. 가장 효과적인 대응은 **오답 문항 쿨다운**
(오답 시 N분간 재출제 금지) 하나로, 컬럼 1개 + 조건 1줄이면 공격 비용이 수천 배 오릅니다.

필요하시면 따로 정리해 드리겠습니다.
