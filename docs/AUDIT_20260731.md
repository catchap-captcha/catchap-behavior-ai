## A-1. 관리 API 표면이 인터넷에 노출됐다 · **실측**

**증상** — 캡차 전체 API 가 인터넷에서 직접 호출된다.

**재현**

```bash
for p in /api/config /health/ready /admin /api/admin/queue; do
  printf "%-28s %s\n" "$p" "$(curl -s -m 6 -o /dev/null -w '%{http_code}' http://61.109.239.231:8000$p)"

```

**근거**

```
/api/config                  200
/health/ready                200
/admin                       200   ← 라벨링 콘솔 페이지
/api/admin/queue             401   ← 키로 막힘
/api/admin/behavior-shadow   401
/api/admin/clusters          401
```

**영향** — 관리 API 자체는 `X-Captcha-Admin-Key` 로 막혀 있어 즉시 털리지는
않는다. 다만 **남은 방어가 관리자 키 하나뿐**이고, 팀 미완 목록의 "시크릿·관리자키
로테이션"이 아직인 상태에서 공개됐다. 대화 중 노출됐을 가능성이 있는 키가

`/health/ready` 는 모델 버전·정책 모드·DB 상태를 그대로 반환한다. 공격자에게
줄 이유가 없는 정보다.

**수정**

1. 관리자 키 로테이션 (공개 전에 했어야 하는 순서다)
2. `/api/admin/*` 와 `/admin` 을 리버스 프록시나 방화벽에서 사내망으로 제한
3. `/health/ready` 는 상세 필드를 관리자 키 뒤로 옮기고, 공개용은
   `/health/live` 수준(`{"status":"ok"}`)만 남긴다

## A-2. `ALLOWED_ORIGINS` 가 실제로 강제되지 않는다 · **실측**

**증상** — 아무 사이트에서나 캡차를 호출할 수 있다.

**재현**

```bash
KEY=$(curl -s http://61.109.239.231:8000/api/config | python3 -c "import json,sys;print(json.load(sys.stdin)['siteKey'])")
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://61.109.239.231:8000/api/captcha/challenges \
  -H "Content-Type: application/json" -H "X-Captcha-Site-Key: $KEY" \
  -H "Origin: https://evil.example" \
  -d '{"purpose":"signup","risk_level":"high","session_id":"origincheck-abcdefgh"}'
```

**근거**

```
201        ← 차단되면 403 이어야 한다
```

**원인** — `check_origin()` 은 구현돼 있으나 허용목록이 비었거나 `*` 면
그냥 통과한다.

```python
def check_origin(request: Request) -> None:
    allowed = settings.allowed_origins
    if not allowed or "*" in allowed:
        return                      # ← 배포본이 이 경로
```

기본값이 `ALLOWED_ORIGINS=*` 이고(`app/config.py:39`), 배포본이 그 상태로 보인다.
`.env` 실제 값은 권한이 없어 못 봤지만 **동작으로 확인됐다.**

**추가로 발견** — `check_origin` 이 걸린 곳은 두 군데뿐이다.

```
app/main.py:620   create_challenge
app/main.py:720   verify
```

**`behavior-batches` 에는 없다.** 배치는 nonce 가 있어야 하므로 단독 악용은
어렵지만, 방어를 건다면 세 곳이 일관돼야 한다.

**영향** — 단독으로는 "남이 우리 캡차를 자기 사이트에 쓸 수 있다" 정도다.
문제는 A-3·A-4 와 겹칠 때다(A-7 참조).

**수정**

```bash
# 캡차 .env
ALLOWED_ORIGINS=https://<인강 도메인>,https://<프론트 도메인>
```

그리고 `check_origin(request)` 를 `behavior-batches` 에도 추가.

**담당** 김민서 · **비용** 설정 1줄 + 코드 1줄 · **시급** 즉시

## A-3. 프레이밍 차단 헤더가 없다 · **실측**

**증상** — 아무 사이트나 이 캡차를 `iframe` 으로 끼울 수 있다.

**재현**

```bash
curl -s -D - -o /dev/null "http://61.109.239.231:8000/?embed=1&lecture=TEST" \
  | grep -iE "x-frame-options|content-security-policy|frame-ancestors"
```

**근거**

```
(출력 없음)
```

응답 헤더 전체가 `server: uvicorn` 뿐이다. `X-Frame-Options` 도
`Content-Security-Policy: frame-ancestors` 도 없다.

**영향** — 캡차는 **원래 임베드해서 쓰는 물건**이라(`?embed=1`) 프레이밍을
전면 차단할 수는 없다. 하지만 지금은 **허용 대상이 무제한**이다.

**수정** — `frame-ancestors` 를 허용 도메인으로 제한한다. `none` 이 아니라
`인강 도메인만` 이어야 한다.

기존 레이트리밋 미들웨어(`app/main.py:568`) 옆에 붙이면 된다.

```python
@app.middleware("http")
async def security_headers(request: Request, call_next):
    response = await call_next(request)
    allowed = " ".join(o for o in settings.allowed_origins if o != "*") or "'none'"
    # 캡차는 임베드해서 쓰는 물건이라 전면 차단이 아니라 허용목록이어야 한다.
    response.headers["Content-Security-Policy"] = f"frame-ancestors {allowed}"
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["Referrer-Policy"] = "no-referrer"
    return response
```

**담당** 김민서 (원하면 제가 `sw-captcha` 에 패치) · **비용** 10줄 · **시급** 즉시

## A-4. `postMessage` 가 `targetOrigin: "*"` 이다 · **코드**

**증상** — 검증 토큰을 **어느 부모창이든** 받을 수 있다.

**근거** — `src/main.jsx:271`

```javascript
if (embed && window.parent !== window)
  window.parent.postMessage(
    { type: "catchap-verified", token: result.captcha_token, lecture_id: lectureId },
    "*"                              // ← 수신자 제한 없음
  );
```

**영향** — 단독으로는 "임베드한 부모가 토큰을 본다"인데, 정상 임베드에서는
당연한 동작이다. 문제는 **누가 임베드할 수 있느냐**가 A-3 로 무제한이라는 점이다.

**수정** — 부모 origin 을 명시한다. 다만 **클라이언트가 준 값을 그대로 믿으면
안 된다.** 서버가 허용목록을 내려주고 그것과 대조해야 한다.

1. `/api/config` 응답에 허용 embed origin 을 추가 (지금은 `siteKey` 만 반환)

```python
@app.get("/api/config")
def public_config():
    return {"siteKey": settings.site_key,
            "embedOrigins": [o for o in settings.allowed_origins if o != "*"]}
```

2. 프론트가 `document.referrer` 의 origin 이 그 목록에 있을 때만, 그 값을
   `targetOrigin` 으로 쓴다. 없으면 보내지 않는다.

**담당** 김민서 · **비용** 양쪽 몇 줄 · **시급** 즉시

## A-7. ⚠️ A-2 · A-3 · A-4 를 이으면 토큰이 새어나간다

세 항목은 개별로는 낮은 위험이다. **공개 개방과 동시에 하나의 경로가 된다.**

```
① 악성 페이지가 캡차를 iframe 으로 끼운다        ← A-3 (프레이밍 무제한)
② 그 페이지에서 캡차가 정상 동작한다              ← A-2 (Origin 무제한)
③ 방문자가 캡차를 직접 푼다                       (사람이 푼다)
④ postMessage 가 "*" 라 악성 페이지가 토큰 수신   ← A-4
```

**완화 요소** — 토큰은 `lecture_id`·`session_id` 에 묶이고, 서버검증에 사이트
시크릿이 필요하고, 1회용이다. 그래서 **즉시 계정 탈취로 이어지지는 않는다.**

**그래도 문제인 이유** — 이건 "봇이 사람에게 캡차를 대신 풀린다"는 경로다.
저희가 행동 AI 로 막으려던 위협 그 자체를, 프로토콜 밖에서 우회하는 길이다.
공격자는 궤적을 위조할 필요가 없다. 진짜 사람이 풀어주니까.

**셋 중 하나만 막아도 사슬이 끊긴다.** A-3 이 가장 싸다(미들웨어 10줄).

## B-4. 사람 속도로 움직이는 봇이 통과한다 · **실측 (표본 작음)**

**증상** — 직선으로 끌어도 사람 속도면 사람으로 판정된다.

**재현**

```bash
python3 tools/redteam_main_captcha.py --base http://localhost:18000 \
  --style linear --timing real --select one --count 8 --confirm
# 그 뒤 catchap_ai 에서 session_id LIKE 'botprobe-%' 조인
```

**근거**

| 그룹 | 건수 | 평균 human_prob | 최대 | allow |
|---|---:|---:|---:|---:|
| `botprobe linear/real` | 5 | **0.999986** | 0.999999 | **1** |
| `rtbot teleport` | 1 | 0.998315 | — | 0 |
| `botprobe linear/synthetic` | 7 | 0.988212 | 0.999984 | 0 |
| `rtbot jitter_fast` | 2 | 0.000001 | — | 0 |
| `rtbot smart_curve` | 1 | 0.000000 | — | 0 |
| `rtbot robotic_regular` | 1 | 0.000000 | — | 0 |
| `rtbot straight_uniform` | 1 | 0.000000 | — | 0 |

`rtbot straight_uniform` 과 `botprobe linear` 은 **둘 다 직선 + 등간격**이다.
결과가 0.000000 대 0.99+ 로 갈렸다.

**차이는 궤적이 아니라 전달 방식이었다.**

```
rtbot     t += 40  처럼 산술로 시각 생성, 전체 풀이 0.8초 미만, 이벤트 12개
botprobe  실제 sleep + 벽시계, 사람 속도로 수 초, 배치 6개
```

**추정 원인** — 학습·시험에 쓴 봇이 전부 산술 타임스탬프에 1초 미만 완주라,
모델이 **"빠르고 규칙적 = 봇"** 이라는 지름길을 배웠을 가능성이 크다. 실제
자동화(Playwright·Selenium·sleep 루프)는 이벤트 루프에서 시각이 나오므로
그 지름길이 통하지 않는다.

**⚠️ 확실도** — 표본이 5·7·1 건이다. 방향은 뚜렷하지만 **이것만으로 "모델이
느린 봇을 못 잡는다"고 결론 내릴 수 없다.** 각 50건은 필요하다.

**수정**

1. 각 궤적 × 타이밍 조합 50건씩 측정 (도구 준비됨)
2. 확인되면 느린 봇을 학습 데이터에 추가해 재학습
3. 근본적으로는 B-5

## B-5. 계획했던 Pointer 필드가 구현되지 않았다 · **코드**

**근거** — `docs/행동데이터앞으로할것.md` §4.2 (2026-07-17) 이 14개를 규정했다.

```
계획   seq · event_type · t_ms · x · y · x_normalized · y_normalized
       pointer_type · pointer_id · is_primary · buttons
       pressure · width · height · target_role
```

실제 수집(`src/main.jsx` `record()`, `app/main.py` `BehaviorEvent`)

```
type · object_id · x · y · timestamp_ms          ← 5개
```

모델 feature schema 는 `trajectory-only 2.3`.

**누락** `pointer_type` `pointer_id` `is_primary` `buttons` `pressure`
`width` `height`

**계획서에도 없어서 추가로 제안하는 것 둘**

| 항목 | 왜 강한가 |
|---|---|
| `isTrusted` | JS 로 만든 합성 이벤트는 `false`. 순진한 봇을 한 필드로 거른다 |
| `getCoalescedEvents().length` | 진짜 포인터는 프레임 사이 원시 샘플을 들고 있다. **실제 브라우저를 띄우지 않으면 만들 수 없는 값** |

**왜 이게 B-4 의 근본 해결인가**

`(x, y, 시각)` 은 전부 공격자가 원하는 대로 만드는 값이다. 거기서만 계산한
특징은 더 좋은 생성기가 나오면 원리적으로 따라잡힌다. **궤적 밖 신호가 없으면
"사람처럼 푸는 봇"에 대한 구조적 방어가 없다.**

수집 변경 없이 지금 데이터로 시험해볼 수 있는 것이 하나 있다 — **프레임 정렬**.
진짜 `pointermove` 는 화면 갱신 주기(60Hz면 16.7ms)에 정렬되는데 `sleep` 기반
봇은 아무 데나 떨어진다. `timestamp_ms` 만으로 계산되지만 **사람 데이터가
있어야 비교가 된다**(B-3).

**담당** 수집은 김민서, 특징은 조성원 · **비용** 프론트 몇 줄 + 특징 추가

# D. 인강 승급

## D-1. `SUSPICION_SESSION_CONFLICT = 5` 가 임계의 절반이다 · **코드**

**근거**

```python
SUSPICION_SESSION_CONFLICT = 5
BOT_SUSPICION_THRESHOLD    = 10    # 기본값
SESSION_TTL_SEC            = 30
```

409 는 "이어보기"를 누르기 **전** 단계에서 난다.

```
다른 기기에서 열기 → 409 (+5) → "이어보기" 안내 → 누름 → takeover (bump 없음)
```

즉 **정상적인 기기 이동, 그리고 30초 이내 새로고침이 그대로 +5** 다.

그리고 이건 추측이 아니라 **기존 코드가 이미 정상이라고 선언해 둔 동작**이다.

```python
# takeover 상한 — 두 세션이 하트비트마다 번갈아 takeover하면 동시 재생 차단이
# 무력화되므로 별도의 낮은 상한을 둔다.
# 정상 사용(새로고침·기기 이동)은 시간당 수 회를 넘지 않는다.
RATE_TAKEOVER_PER_HOUR = 30
```

**"시간당 수 회" 중 2회면 임계 10 에 도달한다.** 노트북 → 폰 → 노트북 한 번이면
끝이다.

**수정**

| 안 | 내용 | 평가 |
|---|---|---|
| A | `5 → 2` | 한 줄. 5회 누적해야 임계 — "시간당 수 회"와 겹치지 않음 |
| B | 409 가 아니라 **시간당 takeover 횟수**로 판단 | 원리적으로 맞음. 기기 이동과 계정 공유를 실제로 구분 |
| C | 409 직후 같은 학생이 N초 안에 takeover 하면 bump 취소 | 구현이 A·B 보다 번거로움 |

**A 를 지금, B 를 다음 단계로** 권한다. `5 × 2 ≥ 10` 은 관측이 필요 없으므로
시나리오 실행 전에 정할 일이다.

**담당** 하지영 · **비용** 한 줄
