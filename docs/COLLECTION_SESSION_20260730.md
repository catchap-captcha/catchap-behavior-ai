## 0. 무엇을 왜 모으나

후보 모델(`revalidation_two_view_participant_safe_20260722`)의 숫자는 전부
**개발 데이터의 OOF**다. threshold 도 그 데이터로 골랐다.

| | 값 |
|---|---:|
| OOF 전체 Human FRR | 0.11% |
| 최악 참여자 Human FRR | 0.93% |
| OOF Bot ASR | 0.065% |
| 레드팀 밀봉 홀드아웃 직접 자동 통과 ASR | 0.60% |

부족한 건 표본 수가 아니라 **분포**다. 저 20,066건은 이전 수집 도구의 궤적이고,
**메인 캡차(김민서 드래그)에서 나온 사람 데이터는 0건**이다.

7/22 에 스스로 정한 규칙이 이것이다.

> 이 후보는 `candidate`로만 보관하며, CAPTCHA 연결 후 새로 분리된 shadow
> 데이터에서 Human FRR과 Bot ASR을 한 번만 확인한 뒤에야 승격 여부를 판단한다.

## 목표 규모 — 팀 5명 안에서 끝낸다

인원은 팀 5명이 전부다. 그 제약 안에서 **사람 간 편차를 최대한 끌어내는 것**이
설계의 핵심이다. 재려는 게 "총 오탐률"이 아니라 "어떤 사람이 계속 걸리는가"이기
때문이다.

### 입력 장치를 조건으로 쓴다

`sessionStorage` 는 **탭 단위**라, 한 사람이 새 탭을 열면 다른 `participant_id`
가 잡힌다. 이걸 이용해 사람마다 입력 장치를 바꿔가며 블록을 나눈다.

```
1인당 3블록, 블록마다 새 탭
   ① 마우스        20회
   ② 트랙패드      20회
   ③ 터치(휴대폰)  20회      ← 가능한 사람만

5명 × 3블록 × 20회 = 300건 / 조건 그룹 15개
```

**입력 장치가 궤적 분포를 사람 정체성보다 크게 가른다.** 마우스·트랙패드·터치는
속도 곡선도 정지 패턴도 다르다. 새 사용자군이 거부당하는 실제 원인이 대개
여기다. 5명밖에 없는 상황에서 편차를 만드는 가장 정직한 방법이다.

```
300건에서 오탐 0건  →  FRR 95% 신뢰상한 1.0%   (rule of three: 3/n)
블록당 20회         →  조건별 FRR 해상도 5%
```

### ⚠️ 한계는 그대로 적는다

이건 **15명이 아니라 5명 × 3조건**이다. 보고서와 발표에 그렇게 쓴다.

- 팀원은 이 캡차를 이미 여러 번 풀어봤다 — 일반 사용자보다 궤적이 일관될 것이다
- 5명은 연령·기기·숙련도 분포가 좁다
- 따라서 이 결과는 **"이 조건들에서는 걸리지 않는다"** 까지만 말한다.
  일반 사용자 FRR 의 상한으로 제시하면 과장이다

실사용 트래픽이 늘면 shadow 로 다시 재는 것이 정본이다.

## 1. ⚠️ 먼저 풀어야 할 것 두 개

### (1) 캡차가 외부에서 접근되지 않는다 — 블로커

```
http://61.109.239.231:8000   → 연결 불가
https://61.109.239.231       → 연결 불가
```

지금은 SSH 터널로만 닿는다. **팀원들이 접속할 방법이 없다.**

팀 미완 목록의 "공개 주소 개방(방화벽 8000)"이 이것인데, **전면 개방은 권하지
않는다.** 같은 포트에 `/api/admin/*` 가 붙어 있고 `ALLOWED_ORIGINS` 가 아직
`*` 다. 세션 1~2시간을 위해 관리 API 를 인터넷에 노출할 이유가 없다.

**대안 (권장순)**

| | 방법 | 비고 |
|---|---|---|
| A | 참여자 egress IP 만 허용하는 임시 방화벽 규칙 | 한 장소에 모이면 IP 하나. 세션 후 제거 |
| B | 백엔드(210) 의 기존 Caddy 에 리버스 프록시로 `/captcha` 노출 | TLS·도메인 이미 있음. `/api/admin` 은 프록시에서 차단 |
| C | 참여자가 각자 SSH 터널 | 비개발자에겐 무리 |

**A 가 가장 싸고 되돌리기 쉽다.** 한 장소(사무실·카페)에 모이면 된다.

### (2) IP 단위 상한에 걸린다

두 상한 모두 **IP 단위**다. 같은 WiFi 를 쓰면 5명이 한 IP 로 보인다.

```python
max_challenges_per_minute = 30     # 챌린지 생성, IP 당
rate_limit_per_minute     = 300    # 모든 요청, IP 당 (미들웨어)
```

풀이 1회당 요청은 대략 15건이다(챌린지 + 배치 4~6 + verify + 이미지·객체 미리보기).

```
5명이 25초에 1회씩  →  12 solves/min   총 요청 ~180/min   여유 있음
5명이 15초에 1회씩  →  20 solves/min   총 요청 ~300/min   상한에 닿음
```

**5명이면 아슬아슬하게 들어간다** — 10명이었으면 확실히 넘겼다. 다만 다들
속도가 붙으면 상한에 닿고, 그러면 429 가 뜨면서 세션이 끊긴다. 원인을 모른 채
중단되는 것보다 미리 올려두는 편이 싸다.

```
MAX_CHALLENGES_PER_MINUTE=300
RATE_LIMIT_PER_MINUTE=3000
```

세션이 끝나면 **반드시 되돌린다.** 이건 실제 방어 장치다.

```
MAX_CHALLENGES_PER_MINUTE=300

```

## 2. 참여자 구분 — 프론트 수정 없이 된다

캡차가 `session_id` 를 `anonymous_participant_id` 로 실어 보낸다(`44c8b32`, 배포 완료).
프론트의 `sessionId()` 는 `sessionStorage` 기반이라 **탭을 닫지 않는 한 유지**된다.

```
새로고침  → 유지 (같은 참여자로 계속 집계)
탭 닫기   → 새 ID (다른 참여자로 잡힘)
```

그래서 참여자에게 전할 규칙은 하나다 — **탭을 닫지 마세요.**

별도 코드(P01…)를 부여하고 싶으면 프론트에서 `?participant=` 를 읽어 넘기면 되지만,
250건 규모에는 불필요하다.

## 4. 진행 중 모니터링

```sql
-- 참여자별 진행률
SELECT participant_id,
       COUNT(*) AS 시도,
       SUM(quality_status = 'valid') AS 유효,
       MIN(created_at) AS 시작, MAX(created_at) AS 최근
FROM ai_behavior_attempts
WHERE created_at >= '<세션 시작 시각>'
GROUP BY participant_id
ORDER BY 시도 DESC;

-- 전체 진행률
SELECT COUNT(*) AS 총건수,
       COUNT(DISTINCT participant_id) AS 참여자수,
       SUM(quality_status = 'valid') AS 유효건수,
       SUM(quality_reason IS NOT NULL) AS 거부건수
FROM ai_behavior_attempts
WHERE created_at >= '<세션 시작 시각>';
```

**중간에 볼 것**: `참여자수` 가 인원보다 많으면 누군가 탭을 닫은 것이다.
`거부건수` 가 늘면 telemetry 검증에 걸리는 중이니 즉시 멈추고 사유를 봐야 한다.

## 5. 끝난 뒤 — 제가 할 것

```sql
-- 참여자별 FRR (모델이 step_up/block 을 권한 비율)
SELECT a.participant_id,
       COUNT(*) AS 시도,
       SUM(p.recommended_action IN ('step_up','step_up_and_rate_limit')) AS 걸린수,
       ROUND(100 * SUM(p.recommended_action IN ('step_up','step_up_and_rate_limit'))
             / COUNT(*), 2) AS FRR_pct
FROM ai_behavior_attempts a
JOIN ai_model_predictions p ON p.attempt_id = a.id
WHERE a.created_at >= '<세션 시작 시각>' AND a.quality_status = 'valid'
GROUP BY a.participant_id
ORDER BY FRR_pct DESC;
```

### 승격 판정 기준 — 미리 못박는다

```
필수
  유효 표본           >= 250건
  사람                 5명 전원
  조건 그룹(사람x장치) >= 12
  전체 Human FRR      <= 2%
  최악 조건 그룹 FRR  <= 5%   ← 이게 핵심. 총계가 평균을 가리는 걸 막는다
  Bot 저지            미소진 봇 홀드아웃 1개 채점해 ASR <= 5%

하나라도 미달이면 candidate 유지. 숫자를 보고 기준을 고치지 않는다.
```

승격하더라도 **"5명 x 3조건에서 확인"** 이라는 단서를 모델 카드에 남긴다.
표본의 좁은 분포를 감춘 채 production 으로 올리면, 나중에 실사용에서
오탐이 나와도 원인을 되짚을 근거가 없다.

마지막 줄이 중요하다. 결과를 보고 기준을 만들면 그건 지금 후보를 정당화하는
일이 된다.
