## 1. 무엇을 막으려고 했나

**말할 내용**

인강 사이트에서 가장 흔한 부정은 대리 시청입니다. 자동화 프로그램이 강의를 틀어놓고
중간에 나오는 확인 절차를 대신 통과합니다. 사람이 안 봐도 수료가 됩니다.

저희 서비스는 시청 검증형이라 이게 곧 서비스의 근간입니다. 그래서 확인 절차를
자동화가 뚫지 못하게 만드는 것이 제 과제였습니다.

```
사용자 → 강의 시청 → 중간 확인(캡차) → 계속
                          ↑
                    여기를 자동화가 뚫는다
```

---

## 2. 캡차만으로는 부족하다

**말할 내용**

캡차는 "문제를 풀 수 있는가"를 봅니다. 그런데 요즘은 이미지 인식이 쌉니다.
멀티모달 모델에 이미지와 문항을 넣으면 학습 없이 답이 나옵니다.

그래서 **"무엇을 풀었는가" 말고 "어떻게 풀었는가"** 를 보기로 했습니다. 사람의 손과
프로그램의 좌표 생성은 다릅니다.

```
캡차        무엇을 풀었나   ← 시각 인식이 뚫음
행동 판별    어떻게 풀었나   ← 이 발표의 주제
```

---

## 3. 어떻게 동작하나

**말할 내용**

캡차를 푸는 동안 포인터 이벤트를 200ms 단위로 서버에 저장합니다. 검증할 때는
클라이언트가 보낸 값을 다시 믿지 않고, **서버가 보관한 것만으로** 채점합니다.

궤적에서 특징 50개를 뽑아 두 모델로 채점하고, 둘 중 낮은 쪽을 씁니다. 어느 한쪽만
이상해도 위험으로 잡히게 하기 위해서입니다.

```
포인터 이벤트 → 서버 저장 (nonce + HMAC 영수증 체인)
             → 검증 시 서버 저장분을 재해싱해 대조
             → 특징 50개 → 두 모델 → min(P_general, P_dynamics)
```

**강조할 점** — 클라이언트를 안 믿는 구조입니다. 봇이 좋은 점수가 나오는 이벤트를
지어내서 보내도 서버가 가진 것과 다르면 버려집니다.

## 4. 결과 먼저 — 회피율 47% → 3.3%

**말할 내용**

처음 보는 공격 방식에 대한 회피율입니다. 47%에서 3.3%로 내렸습니다.
**사람 오탐은 오히려 줄었습니다.** 맞바꿈이 아닙니다.

| | 회피율 | 사람 오탐 |
|---|---:|---:|
| 개선 전 | 47% | 1.62% |
| 개선 후 | **3.3%** | **1.17%** |

승급 기준은 10% 이하입니다.

## 5. 이 프로젝트의 핵심 이야기

**말할 내용**

사실 이 47%라는 숫자를 저희는 **0.7%로 알고 있었습니다.**

저희 레드팀은 봇 궤적을 **무작위로 만들어** 뚫리는 걸 세는 방식이었습니다. 그런데
같은 모델에 시드만 바꿔 여섯 번 돌려봤더니 결과가 이렇게 나왔습니다.

```
회피 28건 · 0건 · 21건 · 18건 · 1건 · 17건
```

**0건이 나온 시드로 봤으면 "완벽하다"고 발표했을 겁니다.**

실제 공격자는 처음부터 다시 뽑지 않습니다. **먹힌 걸 남기고 그 주변을 팝니다.**
그래서 진화 탐색으로 다시 만들었습니다.

```
무작위 스윕    0.7%
진화 탐색      47%    ← 30세대에서 수렴
```

**우리 측정 도구가 공격을 60배 과소평가하고 있었습니다.**

## 6. 그리고 막을 수 있었다 — 안 해봤을 뿐

**말할 내용**

더 놀라운 건 그 다음이었습니다. 7월에 레드팀이 찾아낸 약점 데이터 2,554건이
**학습에 안 들어간 채 그대로 방치돼 있었습니다.**

그걸 학습에 넣으니 회피율이 47%에서 6%로 떨어졌습니다. 특징을 화면 크기와 무관하게
정규화하니 3.3%가 됐습니다.

왜 아무도 안 넣었느냐면, 7월에 **비슷하지만 다른 데이터**로 시도했다가 사람 오탐이
2.4%에서 9%로 튀어 실패한 적이 있었습니다. 그 결론이 "약점 학습은 안 된다"로
굳어졌고, 저도 그걸 확인 없이 받아 적었습니다.

**틀린 결론 하나가 3주를 막고 있었습니다.**

## 7. 구조적 결함 두 개도 측정으로 찾았다

**말할 내용**

**첫째, 채점 단위가 잘못돼 있었습니다.** 특징이 세션 전체 합계라 드래그를 여러 번
하면 값이 커집니다. 그래서 **자로 그은 직선도 다섯 번 끌면 사람 판정**을 받았습니다.
공격자에게는 반복문 한 줄입니다.

드래그마다 따로 채점하니 그 구멍이 막혔고, 동시에 가려져 있던 것이 드러났습니다.
다중 드래그 사람이 통과하던 것은 모델이 알아봐서가 아니라 **합계가 부풀어서**였습니다.

**둘째, 특징이 화면 크기에 딸려 있었습니다.** 50개 중 17개가 픽셀 단위라, 캡차 크기가
바뀌면 같은 손동작이 다른 숫자로 들어갔습니다. 비율 좌표로 바꾸니 성능이 오히려
좋아졌습니다. 절대 크기는 신호가 아니라 잡음이었습니다.

## 8. 못 막는 것 — 정직하게

**말할 내용**

무엇을 못 막는지도 측정했습니다. 이게 없으면 방어를 과신하게 됩니다.

| | |
|---|---|
| **사람 대행 서비스** | 사람이 직접 풉니다. 행동으로는 원리적으로 불가 |
| **시각 인식 봇** | 문항 1,796개는 75분이면 전량 수집됩니다. 그 뒤로는 조회만 |
| **재생 조작** | 배속·탭 숨김은 포인터를 안 건드립니다. 지금 신호를 아예 안 받습니다 |

세 번째가 인강 사이트에서 제일 흔한 부정인데, **저희 방어가 0입니다.** 다만 싸게
잡힙니다 — 서버가 이미 받고 있는 진도와 실제 경과 시간의 비율만 보면 됩니다.
공격자가 못 속입니다.

## 9. 그래서 승급했나 — 아니오

**말할 내용**

성능은 기준을 통과합니다. 그런데 승급은 안 했습니다.

**성능이 부족해서가 아니라, 통과했다고 말할 근거가 부족해서입니다.**

| 항목 | 기준 | 현재 |
|---|---|---|
| 미지 공격 회피율 | ≤10% | **3.3%** ✅ |
| 알려진 봇 통과 | ≤5% | 3.6% ✅ |
| 검증용 참여자 | 5명 | **2명** ❌ |
| 봉인 시험지 | 필요 | **소진** ❌ |

검증용 데이터를 봉인해두고 마지막에 딱 한 번만 채점하는 규칙이 있는데, 그 시험지를
다 써버렸습니다. 새로 모으는 것 말고는 방법이 없습니다.

**7월 30일에 결과를 보기 전에 기준을 못박아 뒀고, 33%라는 나쁜 숫자를 보고도
고치지 않았습니다.** 지금 기준을 만족시키려고 고치면 그 기록이 의미를 잃습니다.

## 10. 3주 동안 숫자를 네 번 뒤집었다

**말할 내용**

마지막으로 이 프로젝트에서 가장 많이 배운 것을 말씀드리겠습니다.

```
"오탐률 0.11%"        → 실제 표면에서 33%      학습 데이터가 다른 화면이었다
"오탐률 1.5%"         → 처음 보는 사람 4.5%    답을 본 데이터에서 쟀다
"이건 못 막는다"       → 3.3%                  레드팀이 약했다
"검증 한 번도 안 받음"  → 이미 받았음            파일 이름만 보고 판단했다
```

**네 번 다 우리에게 유리한 쪽으로 틀렸습니다.** 검증을 안 했으면 좋은 숫자를 들고
이 자리에 왔을 겁니다.

그래서 이번에 만든 것 중 절반이 **측정 도구**입니다. 봉인 대장 검증기는 홀드아웃으로
표시된 데이터 세 개가 사실 학습 데이터라는 것도 찾아냈습니다.

**방어를 만드는 것보다 방어를 정직하게 재는 것이 어렵습니다.**

## 예상 질문과 답

**"실서비스에서 봇을 막고 있나요?"**
아직 아닙니다. 점수만 기록하는 상태이고 위젯 연동이 남았습니다.

**"오탐률이 몇 퍼센트인가요?"**
참여자가 2명이라 숫자를 말씀드릴 수 없습니다. 2명 기준으로는 1.2~4.5% 사이인데,
그 폭 자체가 표본이 부족하다는 뜻입니다.

**"3.3%는 믿을 수 있나요?"**
저희가 만든 가장 강한 공격자 기준입니다. 더 강한 공격자를 만들면 올라갈 수 있습니다.
다만 이전 도구가 60배 과소평가했던 것을 감안하면, 지금 숫자가 훨씬 정직합니다.

**"왜 기준을 낮추지 않았나요?"**
7월 30일에 결과를 보기 전에 정했습니다. 숫자를 보고 기준을 고치면 그 기준이
의미를 잃습니다.
