# 위험도 기반 캡차 승급 — 실행 계획

작성: 최성우 (행동 AI) / 2026-07-29
결정: 이상행동 감지 → **메인 캡차(김민서 드래그, GPU `:8000`)** 표시 → 캡차를 푸는 동안 봇 판별

> 이 문서가 `BACKEND_BEHAVIOR_INTEGRATION_PLAN.md`(경로 B, 백엔드 자체 캡차에 이식)를
> **대체한다.** 메인 캡차가 김민서 드래그 캡차로 확정되어 이식이 필요 없어졌다.

---

## 0. 왜 이 설계가 지금 유일하게 실행 가능한가

지금까지 AI를 실제 판정에 쓰지 못한 이유는 **오탐률 미측정**이었다. 그런데 승급 방식은
오탐의 대가가 다르다.

```
기존:  캡차 통과 → AI 가 봇 판정 → 차단          오탐 = 정상 사용자 차단
승급:  이상행동 → 캡차 표시 → 풀면 통과          오탐 = 캡차 한 번 더 품
```

**오탐 비용이 "차단"에서 "캡차 1회"로 내려간다.** 실사용 트래픽이 하루 2~4건이라
오탐률을 정밀 측정할 수 없는 현 상황에서, AI를 실제로 쓸 수 있는 유일한 경로다.

## 1. 흐름

```
인강 시청 (백엔드 210.109.52.124)
   │ 이상행동 신호 누적 → 임계 초과
   ↓
"캡차 필요" 응답
   ↓
클라이언트가 메인 캡차 위젯 로드 (lecture_id 전달)
   │                          ┌─ GPU 61.109.239.231 ─────────────┐
   ↓ 사용자가 드래그로 푼다   │  캡차 :8000                       │
                              │    ├ 배치 실시간 수집(nonce+체인)  │
                              │    ├ 서버 저장 배치만 채점         │
                              │    └ AI 호출 → 127.0.0.1:8010     │
                              │  AI :8010 (같은 호스트)            │
                              └────────────────────────────────────┘
   ↓ 통과 시 캡차가 토큰 발급 → 클라이언트가 백엔드로 전달
백엔드 → POST /api/verify-token (site_secret) → 확인
      → 누적 카운터 리셋 → 시청 계속
```

**AI 호출이 같은 호스트 `127.0.0.1`이라 크로스 호스트 노출·방화벽 변경이 전혀 없다.**

## 2. 이미 있어서 만들 필요 없는 것

| 자산 | 상태 |
|---|---|
| 행동 신뢰 프로토콜 (receipt chain·좌표결속·전송타이밍) | ✅ `sw-captcha` 브랜치, 701줄, 테스트 23 통과 |
| 행동 AI (재생 탐지 포함) | ✅ 프로덕션 스키마 대응 완료, 재생 탐지 실증 |
| **인강↔캡차 접점** | ✅ 캡차 `POST /api/verify-token` — "호스트(인강) 서버가 사이트 시크릿으로 호출한다", `lecture_id` 인자까지 있음 |
| 감지 신호 | ✅ 백엔드가 이미 계산 중 (아래) |
| GPU→DB 사설망 | ✅ `10.0.1.168:3306` 도달 확인 |

### 감지 신호는 계산되고 있으나 버려진다

| 신호 | 현재 처리 | 승급 트리거로 |
|---|---|---|
| position 전진 속도 위반 (`SPEED_FACTOR=2.5` 초과) | 클램프하고 버림 | **누적** |
| 동시접속 충돌 | 409 던지고 끝 | 누적 |
| 체크포인트 연속 오답 (`MAX_CHECKPOINT_FAILS=3`) | 되감기 | 누적 |
| 규칙 기반 위험도 `_behavior_risk_level` | 계산 후 미활용 | 누적 |

**새 탐지 로직이 필요 없다. 누적할 자리와 임계값만 있으면 된다.**

⚠️ `lecture_watch_progress.suspicion` 컬럼이 그 자리였는데 **2026-07-17에 의도적으로
제거**됐다("시청-감시 설계의 잔재" → 학습 강화 설계로 전환). 컬럼은 남아 있어 되살리기는
쉽지만, 되돌리는 결정이므로 김태형과 합의가 필요하다. 목적이 "감시"가 아니라 "봇 판별"로
달라진 점을 설명하면 될 것으로 본다.

## 3. 단계

### Step 1 — GPU AI 갱신 + DB 연결 (나, 반나절)

**현재 GPU AI는 2026-07-28 재매핑 이전 코드다** (git 체크아웃이 아니라 복사본).
그대로면 프로덕션 스키마에서 읽기·쓰기 모두 실패한다.

- [ ] 새 코드 전송 (백엔드에 한 것과 동일한 rsync — `app/`, `learning/`, 모델)
- [ ] `.env`에 추가: `MYSQL_HOST=10.0.1.168`, `MYSQL_DATABASE=catchap_dev_db`,
      `MYSQL_USER`/`MYSQL_PASSWORD` (백엔드와 동일 계정, **URL 디코딩된 값**)
- [ ] `cryptography` 설치 (MySQL 8.0 caching_sha2_password용 — 없으면 첫 접속만 실패하는 간헐 증상)
- [ ] 재기동 → `mysql_connected:true` 확인
- [ ] 동일 궤적 3회 투입 → `exact_replay=True` 재확인

백엔드(.124) AI는 그대로 둔다. 캡차가 백엔드로 이전할 때의 목적지가 된다.

### Step 2 — `sw-captcha` 재병합 → 푸시 (나, 반나절)

`ms`가 3커밋 앞서 있다 (지시문 재번역·관리자 검수 개선). 소스는 자동 병합되고
**충돌은 `static/dist/` 빌드 산출물뿐**이다.

- [ ] `git merge origin/ms`
- [ ] `npm run build` (충돌 해소가 아니라 재생성)
- [ ] 테스트 23개 확인
- [ ] `git push -u origin sw-captcha`

### Step 3 — 캡차 배포·설정 (김민서, 10분)

- [ ] `sw-captcha` 배포
- [ ] `BEHAVIOR_EVENT_TRANSPORT=off` → **`shadow`**
- [ ] `BEHAVIOR_AI_URL=http://127.0.0.1:8010` (기본값이면 그대로)
- [ ] `BEHAVIOR_AI_BACKEND_KEY` — **변경 불필요.** GPU AI의 기존 키를 그대로 쓴다
- [ ] `BEHAVIOR_POLICY_MODE=shadow` 유지

### Step 4 — 백엔드 승급 로직 (김태형 + 나, 1~2일) ← 유일한 신규 코드

- [ ] 신호 누적 필드 (`suspicion` 재활용 또는 신규)
- [ ] 임계값 정의 — 초기엔 보수적으로 (예: 속도 위반 3회 또는 동시접속 충돌 2회)
- [ ] 임계 초과 시 응답에 "캡차 필요" 플래그 + `lecture_id`
- [ ] 프론트: 플래그 수신 시 메인 캡차 위젯 표시
- [ ] 통과 토큰을 백엔드가 `POST /api/verify-token`으로 검증 → 카운터 리셋
- [ ] 검증 실패/토큰 없음 → 시청 진행 차단 (여기는 fail-closed가 맞다)

## 4. 일정

| Step | 작업 | 소요 | 담당 |
|---|---|---|---|
| 1 | GPU AI 갱신 + DB | 0.5일 | 나 |
| 2 | 재병합 + 푸시 | 0.5일 | 나 |
| 3 | 캡차 배포·설정 | 10분 | 김민서 |
| 4 | 백엔드 승급 로직 | 1~2일 | 김태형 + 나 |

**총 2~3일.** 경로 B(6~7일)의 절반 이하다. 이유는 이식이 없어졌고 인강 접점이 이미 있기 때문.

## 5. 되돌리기

- 캡차: `BEHAVIOR_EVENT_TRANSPORT=off` → 기존 동작과 100% 동일
- 백엔드: 임계값을 무한대로 → 승급이 발생하지 않음
- GPU AI: `.env`에서 MYSQL_* 제거 → 기존 상태(`mysql_connected:false`)

## 6. 단계적 강화

```
1단계  shadow — AI 점수 기록만. 승급은 규칙 신호로만 발생          ← 여기서 시작
2단계  수집된 데이터로 오탐률 측정 (승급 트래픽이 표본이 된다)
3단계  AI 점수를 승급 판정에 반영
4단계  AI step_up 을 캡차 재출제에 반영 (오탐률 목표 충족 후)
```

**1단계만으로도 지금보다 낫다.** 이상행동에 캡차가 뜨고, 그 캡차는 행동 신뢰 프로토콜로
위조를 막는다. AI는 shadow로 관측만 하며 데이터를 쌓는다.

## 7. 이 설계가 막는 것

| 공격 | 결과 |
|---|---|
| position 위조로 진도 채우기 | ✅ 이미 막힘(속도 상한) + 이제 **캡차 승급까지 발생** |
| 체크포인트 자동 통과 | ✅ 행동 신뢰 프로토콜 |
| 궤적 위조 | ✅ 서버 저장 배치만 채점 |
| 사람 궤적 재생 | ✅ receipt chain + AI DTW |
| 동시접속 계정 공유 | ✅ 이미 막힘 + 캡차 승급 |

**못 막는 것**: 사람 대행, 완벽 페이싱 재생(±400ms), 시험 자동화(별건 — `course_exam_*`에
시간제한·속도하한·레이트리밋·캡차 전무), 영상 유출(범위 밖).
